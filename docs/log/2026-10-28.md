### 2026-10-28 —— 供应链补刀：**markdown-it 钉 ≥14.3.3（结 GHSA-vfgh-jcmw-g37q，js-tests 账外红结算）**

第十三批起挂账的 js-tests 红（`npm audit --audit-level=low` 报 markdown-it <=14.3.2 的
inline HTML 二次方 DoS advisory）**结算**。typedoc 0.28.20（latest，lock 在装）依赖 range
仍是 `^14.3.0`，会解析到受影响的 14.3.2 —— 升 typedoc 无解，走 **npm overrides**
（`bridge/js/package.json` 加 `"overrides": {"markdown-it": "^14.3.3"}`）。lock 同步：
本机禁跑 npm（构建/安装一律走 CI），lockfile 无法本机重解析 —— 用 registry 的精确
integrity 手改 `node_modules/markdown-it` 一条（version/resolved/integrity 三处），
改完由 CI 的 `npm ci` + `npm audit` 实测验过才算数（若 ci 因 lock 手改报 integrity
不符即红，属于本补刀的账，就地再修）。

### 2026-10-28 —— 依赖页第十七批：**裁掉安装行下的重复日志 + 第十六批对照实验收官**

**第十六批收官（对照实验结论）**：用户装机实测 —— 「**release版本确实很流畅**」。
病在包形态，代码无罪：`debuggable=true` 的包（解释 + JIT、dex 不过 R8）本身就贵一个
量级，前几批优化省下的每帧小钱被包形态淹没。**后续评分一律用 release 包**（真形态
管线 debug + release 双出已常态，`android-release-true-form`）。

**第十七批（2026-10-28，用户口径原文）**：「**去掉安装依赖下面会输出日志（目前它的下面
和日志框里都会显示，只保留日志框里的就行）**」。

**改法**（`NpmScreen.kt` 的 [InstallProgressRow]）：只画六格阶段条。
- 进行中的阶段文字行（label + 包名）去掉 —— npm 自己的输出在日志框里讲同一件事；
- 收尾（[InstallProgressState.done]）后**整段收起**，不再画「装完 / 失败：病因」结论行
  —— 失败进 `opError`、成功在 npm 输出与「已提交」回执，日志大框一家承担。
- **阶段条不是日志，照画**：那是批 87（2026-10-09）要的进度反馈，不识字也读得懂
  亮到第几格。

**状态的边界**：`InstallProgressState`（`label`/`detail`/`done`）与 `foldProgress`
的组装一行未动 —— 那只删了呈现层的两个绘制点，宿主契约照旧（`label` 从此在界面
上不再出现，但状态与测试仍以它为真相）。

**与前一节的账分**：十六批的「release 流畅」是用户实测结论，这节是 UI 呈现裁剪，
两件事各记各的批号，避免「性能问题解决了」被误读成「这个改动让 release 变流畅」。

### 2026-10-28 —— 依赖页第十六批：**性能形态对照 —— 真形态管线加出 release 变体**

用户口径：问「卡顿问题有修复思路吗」→ 提出「真机一直测的是 debug 包」→ 拍板把
release 变体并进本批（授权解冻 `.github/workflows/engine-native.yml` 这一处）。

**发现**：真机复测（engine-native 出包）一直在 **debug 形态**上做 —— `assembleDebug`
出的包 `android:debuggable=true`，ART 只做校验级编译（跑起来是解释 + JIT），dex 也没过
R8；Compose 官方口径是「**评性能必须 release + R8**，debug 下 LazyColumn 卡顿是常态」。
第十三~十五批去掉的是**每帧的小钱**（分配、陪跑重组、全屏圆角裁剪、列表形状），在解释
执行的包上收益会被淹没 —— 这解释了「三批优化、真机依旧卡」。

**改法**（`engine-native.yml` + `app/proguard-rules.pro`）：
- 同一个 gradle 调用出 `assembleDebug :app:assembleRelease` 两个变体；断言块提成函数对
  两包**同跑一遍**（`.so`/assets 不进 dex 不被收缩，同判据该同结果，变了就是收缩链路的账）；
  新增 artifact `android-release-true-form`。
- release 走**既有** buildType：R8 全量 + 资源收缩 + 仓库 dev 密钥（与 debug 同一把，
  两端可互覆、不用卸载）。
- R8 风险复核：`proguard-rules.pro` 的反射面清单逐条再对 —— `Class.forName` 3 处、
  `getMethod` 9 处的账依旧成立；**逮到一处注记过期**：审计写的时间早于 `:platform:process`
  模块（批 105），现在 `getDeclaredField` 有 1 处（`ProcOps.pidOf` 的 pid 两级阶梯）——
  结论不变（反射目标全在 java.lang 平台类上，不参与收缩），已原地加复数勘误注记。

**预期的两种结局**（这是实验，不是又一次凭猜修）：
- release 不卡 → 病在包形态，代码无罪；以后评分（含前几批到底有没有用）一律用 release 包。
- release 还卡 → 才轮到行物理 / 设备档次的账，那时再谈第十五批之后的代码侧候选。

**诚实边界**：本机测不了帧率；等用户装机对比 debug / release 两个包的手感。

### 2026-10-28 —— 依赖页第十五批：**清单收回定高内滚框（第十二批第 31 条的摊平作废）**

用户口径原文：「**还是很卡顿，依赖列表你不要让它完全展开。而是在一个组件框里滑动**」。
第十四批（稳态剥壳）落地后真机依旧卡，用户直接给了结构裁定 —— 这次是**用户点名要的结构**，
不是再猜一处渲染开销。

**改法**（`NpmScreen.kt`）：展开态不再把每颗依赖摊成页面 `LazyColumn` 自己的 item，而是收成
**一条 item** —— 卡内一个 `heightIn(max = 320.dp)`（约 7 行）的定高框 `DepsListBox`，框内
自己的 `LazyColumn` 懒加载各行。页面滚动只剩作用域卡 / 这一组（3 条 item）/ 日志卡三段；
翻清单时动的只有那个框。拖动归属走嵌套滚动缺省：框没到头归框、到头归页面。
**作废第十一批第 31 条**（摊平 + 全页只留一个可滚动容器，2026-10-18）：摊平后整页是一条由
全部依赖行组成的长列表，行物理与组合的钱全在这一条链路上付；当年拆卡内自滚的顾虑
（"两层竖向滚动要交接"）在定高框形状下不成立。文件 KDoc 第十二批第 32 条原地记账，
第 31 条原地划掉注明。

**与第十四批的关系**：两刀切的是不同层 —— 第十四批去的是"顶层那层每帧整屏圆角裁剪"，
这一刀去的是"滚动负载落在整页长列表上"。若真机仍卡，剩下的候选就只有行物理本身
（几百行一帧涌进视口的排版成本，框内懒加载已把它限在 ~7 行视口）与设备档次。

### 2026-10-28 —— 依赖页第十四批：**ManagementTransition 稳态剥壳（顶层裸直绘）**

用户口径原文：「**翻动起来还是很卡啊，认真优化好不好。翻起来列表一顿一顿的**」。第十三批后
真机（engine-native 真形态 APK）依旧卡 —— 而第十三批的 premise 已在上面被证伪，卡顿与轮询
发布无关，纯渲染侧。

**排查逐层排除**：轮询不发布状态（`pollWhile` 只写局部 var，证伪标注见上一批）；`snapshot()`
整趟 `Dispatchers.IO`（2026-10-17 已修，不掐主线程）；行单元静态（Text×3 + Glyph 常量化 +
两粒无动画 pressable）；contentType/key 正确；顶层 `graphicsLayer`/`alpha` 恒等值下 Compose 1.7
不建离屏层。**剩下与首页（pager 里那份，用户说不卡）唯一的渲染路径差异**：依赖页是
`ManagementTransition` 顶层 —— 稳态也由 `alpha + graphicsLayer + Box.clip(全屏圆角)` 三层包着，
`Modifier.clip` 那层**每帧都给整屏滚动内容重做一次圆角裁剪路径**（非矩形 clip 在 HWUI 走
stencil/clip layer，低端 GPU 上正是「一顿一顿」的经典来源），首页没有任何一层。

**改法**：顶层加 `settled` 判据（`progress == 1 && dismiss == 0 && 无手势 && innerTranslationX == 0`）：
稳态走**裸直绘** —— `Box { content }`，三层包装一个不留（圆角裁剪在稳态本来就不可见：
顶层铺满全屏，物理屏幕自己裁四角；裁剪只在窗口缩小的动画期间有意义）。动画/手势一开始
判据即破、包装挂回，同一帧快照内完成，不闪。`claimPointerHits`（挡触穿）是功能不是动画，
两路都留。

**诚实的边界**：若真机上这刀仍不解决，剩下的结构性差异就只有行物理（几百行一帧涌进视口的
排版成本）与设备档次 —— 那需要真机二分（收起态滑 vs 展开态滑），用户已拒绝二分改走直接修。

四个条件超阈值。修法是**把判据提成私有函数**（不是砍条件）：语义逐字不动，四条注释
（快照判等的来由 + 失败态、操作账两个排除项的账）原样跟过去，三条 `===` 用例不动。
同批另一处红（js-tests）**不是本批的账**：`npm audit --audit-level=low` 报 markdown-it

### 2026-10-28 —— 依赖页第十三批：**Glyph 坐标提成常量（绘制期零分配）+ 状态「没变就不换引用」短路（轮询期不再整屏陪重组）**

**用户口径原文**：「**依赖列表展开时，滑动特别卡顿**」。

第十二批（10-18）已经去过一轮白扔（派生属性算一次、`@Immutable`、contentType 分开、
行内胶囊不带动画、Glyph 的 Path/Stroke 池子）。这批接着去**剩在热路径上、上批没点名**的两处
（老规矩：本机测不了帧率，禁 Gradle / 禁设备 / 禁 adb 截图读屏 —— 逐条指名道姓地去掉浪费，
不把「去掉了浪费」讲成「已经不卡了」）：

**一、Glyph 绘制 lambda 每帧仍在分配（第二刀）**。10-18 那批的 `GlyphScratch` 池子只覆盖了
`Path` 与 `Stroke`，坐标那一路还漏着：`path(0.19f to 0.36f, …)` 的 **vararg 数组、`Pair` 与
装箱 `Float` 是在调用点现造的** —— 而 `when (kind)` 整段每帧重跑一遍，于是每个可见字形每帧
仍要造十几个小对象。展开的依赖列表一行一颗 ⟳，滚动时就是**每帧上百个** —— GC 是「一段时间
里攒出来的一次停顿」，帧率读屏看到的就是一阵一阵的卡。改法：**84 处 `path(...)` 调用点的坐标
整体提成文件级常量**（`P_<字形>_<笔名>`，`Array<out Pair<Float, Float>>`，类加载时建一次），
`path()` 签名从 `vararg Pair` 改为收这份常量；数值逐字相同、字形几何一条未动，绘制期零分配。

**二、状态「没变就不换引用」（第二刀）**。`NpmState.of` 无条件从快照重建、`pollInstallEvents`
无条件 `copy` —— 而 `npmSnapshot()` 每次回读都造一份**内容相同**的快照（量尺寸那趟走完
node_modules，数字没动）。LazyColumn 的 item lambda 捕获的是 state **引用**，换一份等值的也是
换 —— 安装轮询（每 400ms 一 tick）进行中，~~**展开的整屏可见行每 tick 重组合一次**~~（~~2026-10-28 第十四批复核证伪：`pollWhile` 的循环只写局部变量，`npmState =` 只在轮询结束发生一次，轮询期间页面**从不**重组 —— 本次短路修的是一段不存在的开销，保留只因其无害~~），滑到一半
被打断正是「展开时滑动特别卡」的来路之一。两处短路：

- `NpmState.of`：`snapshot == previous.snapshot`（data class 内容判等）且无失败态、无操作账
  （`opError`/`opNotice` 为 null）→ **原样复用 previous**。两个排除项各有各的理由：
  `LoadState.Failed` 只改 `load` 不动快照，短路会把「读取失败」这句错话留在日志框里；
  `opNotice` 的 KDoc 本来就写着「**现取即清**」，重建那份把它归 null 是这句注释原本答应的行为。
- `pollInstallEvents`：事件游标没推进（`batch.lastSeq == since`）且阶段没变（folded 相等）→
  **原样返回同一份**，不 `copy` 等值实例。

三条新测试钉这三条（`NpmStateTest` 两条、`NpmInstallOpsTest` 一条），全部用 `===` 断**引用**
而不是值 —— `copy` 出来的同值对象救不了重组，只有原样复用才救得了。

**没动、也说明白的**：第十二批第八条那个「为什么首页不卡」的待测数依旧开放（依赖条目量级 /
控制台页与日志管理页是否也卡 / `ManagementTransition` 那两层全屏 `graphicsLayer`）—— 这批没
再往那两层上猜。安装轮询期间**事件真在推进**时的重组（阶段条前进）是合理成本，没为了省重组
把阶段条挪出状态 —— 那是另一笔账。

### 2026-10-11 —— 批 100：外审整改第五刀 —— 桥在途字节闸（M2 的可做那半）

**背景**：外审 M2 那条列了三件事。本批只做**第三件（字节闸）**，另两件如实登记不做
（理由见下）。先做它的理由：它是**两个已生效默认值相乘就能得到的数** ——
`maxFrameBytes`（8 MiB）× `maxInFlight`（256）= **2 GiB 堆**，在 minSdk 26 的设备上直接 OOM，
而那一刻的现场是「脚本发了一堆大请求把宿主撑死」，看不出是哪条面干的。

**① 在途请求字节闸（`maxBytesInFlight` = 16 MiB）**。原口径只有**条数**闸（256）——
而**条数与字节正交**：一条 8 MiB 的帧能过掉条数闸，256 条就是 2 GiB。与批 99 给 zip 加
`MAX_ENTRIES` 是同一条纪律（计数与字节正交，各设一闸）。
- **CAS 而不是 `synchronized`**：这一段每条请求都要走，`synchronized` 会变成全局竞争点
  （所有连接的读循环都串行过一次）；无竞争时是一条 CAS 指令。
- **单条超上限直接拒，不做「部分接纳」**：一条 8 MiB 帧配 1 MiB 上限，部分接纳等于让
  请求**永远等不到** —— 不如立刻拒。
- **拒的是这一条，不是整条连接**：被拒的请求**回一帧 `ERR_PERMISSION_DENIED`**（话术点名
  「字节」，免得与条数闸混淆），连接继续服务后续小请求。**不静默丢** —— 静默丢的话脚本只会
  干等到 TTL 超时，那才是真正的坑。

**② 同条另两半如实登记不排期**：
- **每连接配额** —— 现在一条连接可以吃满全部 256 条在途（其他连接的请求全被挤在门外）。
  要做就得连同「连接级计数的可见面」一起设计，否则会重演「三处记账手拿会漂」那类问题
  （批 96 在池记账上刚踩过同一条的变体）。
- **`limitedParallelism`** —— 本类 [scope] 直接用 `Dispatchers.IO`（默认 64 线程），
  连接数上去时读线程与其它 IO 用途抢同一个池。

**守卫先红后绿**：`NewlineFrameServerByteQuotaTest` —— 字节上限 4 KiB + 帧上限 64 KiB
（**刻意让字节闸先撞**，否则测到的是帧闸），断言①8 KiB 的请求被拒且回帧点名「字节」，
②之后 1 KiB 的小请求**照常被受理**。把字节闸短路掉（`if (false && …)`）该用例当场红。

### 2026-10-11 —— 批 99：外审整改第四刀 —— shell 杀树与 stdin 关闭（M6）+ zip 三条硬化（M7）

**背景**：外审剩下两条「本机可验、纯工程」的：M6（shell 面）与 M7（zip 面）。批 98 之后
剩下的是 B2（池重构）、M2（桥限额）、M9（要拍板）与结构性项 —— 都不属本批。

**① M6-a：shell 收尸从「只杀直接子进程」变「杀整棵树」**。原 KDoc 写着「不留孤儿进程」，
**那句话不成立** —— `destroyForcibly()` 只杀 `sh`/`su`，它们自己起的孙进程
（`sh -c "sleep 300 &"`）留在设备上，而「越跑越卡」这种现场查不到源头。修法：
`AndroidShellExecutor` 加 [killTree]（`/proc` ppid 图 + `kill` 二进制 + pid 两级反射阶梯）
与 `TreeOps` 缝（可注入替身），超时路径与 `finally` 都改走它。
**顺带订正一个我自己写出来的顺序错**：初版是「`destroyForcibly()` 主进程 → 再点名后代」，
而批 95 的纪律是**扫/点名在杀之前**（`/proc` 扫描更怕的是 reparent，pid 集合在树还活着时
到手才稳）—— 改成**先点名后代 TERM → 再杀主进程 → 立刻补 KILL**（收尸路径不等宽限）。
**诚实降级**：pid 取不到 / `/proc` 不可读 → 空集 → 只杀主进程（不更坏、不假装收干净）。

**② M6-b：stdin 立即关闭**。shell 面的契约是「只执行命令、不喂输入」（`ShellExecutor.exec`
签名里根本没有 stdin 参数），但原实现攥着写端不撒手 —— 于是等输入的命令（`cat`、`read x`）
**一直挂到超时**，用户看到的是「一条 cat 跑满超时返回空」。启动后立刻
`process.outputStream.close()`：它们读到 EOF 正常退出，那才是「没有输入」该有的形态。

**③ M7：zip 面三条硬化**。
- **条目数闸（`MAX_ENTRIES` = 1 万）**：一个「零字节 × 50 万条」的归档能过掉单条与合计两道
  **字节**闸（合计 0、每条 0），却要造 50 万个 inode。**计数与字节正交**，必须单独设闸；
  与字节闸同层（zip-slip 同层），同样**先验后写**（不合格的包一个字节都不落）。
- **`.tmp` 不自含**：归档写进**源目录内部**时，`Files.walk` 会走到本次的 tmp（zos 打开
  那一刻它就存在）—— 包把自己包了进去。判据用**绝对路径相等**（不用 `startsWith(source)`
  前缀比较：源目录名是别的目录名前缀时会误判）。
- **`walk` 的 `UncheckedIOException`**：它**不是** `IOException` → 原 `catch (e: IOException)`
  接不住 → `deleteIfExists(tmp)` 被跳过、错误码也不是 `ERR_IO`。改为在 walk 迭代段折成
  `IOException` 再抛。

**④ 两份 `ProcOps` 的关系（主动记下来，别当成疏忽）**：本批在 `:platform:system` 新增的
`ProcOps` 与批 95 在 `:app-service:npm` 的那份**手法逐字同款但代码两份** —— 被依赖方向逼的
（两模块都只依赖 `:domain`，而 `/proc` 是进程/文件系统面不是领域概念）。两份 KDoc 互相点名，
**改一处必须看另一处**。真要消重得抽一个「进程工具」模块（模块表变更，要维护者拍板），
本批不做。

**守卫（先红后绿）**：`AndroidShellExecutorReapingTest` 四例（stdin 关 / 超时点名整棵树
含顺序账 / pid 取不到的降级档 / **真 `/proc` 真 `kill`** —— 替身钉顺序与点名，真进程钉
`/proc` 面数得对，两者分开钉；批 95 的 npm 侧同款分工）、`JdkZipArchiverHardeningTest`
三例（条目数闸 / tmp 不自含 / 失败不留半截 tmp）。其中 tmp 那条**先红后绿**已实测
（去掉 `skipTmp` 即当场红）。

### 2026-10-11 —— 批 98：外审整改第三刀 —— accept 遇瞬时故障不再收掉整条桥（M3）

**背景**：批 96/97 做了外审的高危与中危里那些「单条语义改动」的；本批做 M3 ——
**两处 accept 循环都是同一族病灶**，且都是「一次就死整条桥」。

**病灶**：`catch (_: IOException) { break }`。`IOException` 是个**家族**：本端 `close`
顶醒 accept 是「该停了」，而 `EMFILE`（fd 用尽）/ `ENFILE`（系统表用尽）/
`ECONNABORTED`（内核踢掉半开连接）都是**瞬时**的 —— 一次就 break 等于**整条桥对所有未来
脚本静默死亡**（无日志、无重启、无自愈，现场表现是「脚本再也连不上」且查不到源头）。

**现口径（本端关断判据与实现面各自合适）**：
- 已 close（监听面 `running == false` / 帧服务 `listener` 已移除）→ 收循环；
- 瞬时错 → 计数 + **退避 1s 后重试**，连续 **20** 次才收（那种情形已经不是瞬时的了；
  无限重试 = 一个永远转不出结果的线程 + 桥看起来还活着，两头都骗）；
- 非 socket 类异常 → 照旧收（那是代码 bug，不该被重试掩盖）；
- 退避用 `retryGate.wait()` 而非 `Thread.sleep`：关断要能立刻唤醒它 —— 否则「用户点了
  急停、线程还赖着 1s」那条路就白修了。

**两份独立实现各修各的**：`BridgeSocketListener`（设备 `LocalServerSocket` 面）与
`NewlineFrameServer`（本机 TCP 面）。用 `SocketException` 而非 `IOException` 是有意的 ——
前者只从 accept 这一个调用点抛出，语义精确；后者把「已关断」与「系统压力」混在一起。
**两份必须各钉一次**：修一份不修另一份，另一份照样静默死亡。

**诊断面**：两条各加 `acceptRetryCount` 与失败回执缝（与 `rejectedCount` 同一纪律：
拒绝要能数，故障也要能数；此前这里**什么都没有**，死起来一点痕迹都不留）。退避时长可注入
（单测 1ms，不真等 1s）。

**守卫先红后绿**（把阈值改成 1 即模拟「首次失败即收桥」，两条当场红）：
`BridgeSocketListenerAcceptRetryTest`（抛 3 次瞬时错后错 token 的 hello 仍拿到 helloErr）、
`NewlineFrameServerAcceptRetryTest`（抛 1 次瞬时错后仍完成 helloAck）。判据用**可观测
行为**（「桥还活着」= 握手仍能完成），不用内部状态 —— 将来把重试逻辑挪走照样红。

**验证**：CI 逐字同源 14 测试任务全绿零失败零跳过；detekt 全模块绿；全仓零跳过。

### 2026-10-11 —— 批 97：外审整改第二刀 —— ERR_INTERNAL 与折叠两档 / kv 迁移表 / pid 第二级（M4·M5·M8）

**背景**：批 96 做了外审的 B1/B3半/B4半 三条；本批做剩下的**三条单条语义改动 + 守卫**
（M4 错误映射、M5 pid 绑定、M8 onUpgrade 丢表）。每条都是「改一处口径 + 一对守卫」，
不牵动架构 —— 结构性建议（池重构、typed ids、actor 化）仍未排期。

**① M4：新增 `ERR_INTERNAL`，桥折叠改两档（此前一切折成 `ERR_INVALID_PARAM`）**。
原 `BridgeRouter` 的 `catch (e: Exception)` 把任何未预料异常折成 `ERR_INVALID_PARAM` 并回显
`e.message` —— 脚本 `e.is('ERR_INVALID_PARAM')` 会去改自己的参数（真相在宿主堆栈里），
回显还把内部路径/字段名带进 wire；这**与 `RpcNamespaceHandler` KDoc「未知异常不接、照旧
穿出」直接矛盾**。现口径两档：`AutojsException` 原码透传（SPI 抛的真码不许被吞成
「宿主有 bug」）→ `IllegalArgumentException` → `ERR_INVALID_PARAM`（能读懂的事实）→
**其余一切 → `ERR_INTERNAL`**（读不懂的事实 = 代码缺陷）。两处落字已同步：`:domain`
`ErrorCode` 枚举与 `bridge/js` 的 `ErrCode` + `ERROR_CODES`（由 `err-catalog.test.cjs`
三面对账门钉住）。**契约卷 §7.6 属冻结面、本批撤出**（`check-frozen-paths.sh` 当场红）——
待维护者同步错误目录与折叠两档，补丁已留在批 97 的 `revert(docs)` 提交说明里；不阻塞，
因为该门判据是「文档提到的码两处目录都在」而文档自称是摘录。守卫 `BridgeRouterTest` **三条成对**（内部 → INTERNAL、
参数 → INVALID_PARAM、AutojsException → 原码）—— 少一条即口径漂。

**② M5：pid 取值补第二级反射阶梯（Android 8–12 的防劫持判据不再整段跳过）**。
`Process.pid()` 在 Android 需 API 33 而 minSdk 26 —— 于是 Android 8–12 上 `spawn.pid` 恒 null，
`RunIdentityRegistry` 的 `if (peerPid != null && spawn.pid != null && …)` 两条件都不成立，
**整段防劫持判据静默跳过**。`engine:node-process` 的 `ProcessLauncher` 补私有字段 `pid`
那一级反射（与批 95 `ProcOps.pidOf` 逐字同款手法：tier 1 方法 → tier 2 字段，都探不到
如实 null）；并给 `RunIdentityRegistry` 加 `pidUnavailable` 计数 —— 「跳过」与「度量通过」
在返回类型上长得一样，计数是它唯一的可见信号。守卫 +2（计数命中 / 正常路径不误计）。

**③ M8：kv 升版走显式迁移表，不再「DROP 重建」**。原 `onUpgrade` 版本一升就 DROP 表 ——
脚本可再生数据说丢就丢，且无 `onDowngrade`。抽出 `KvSchemaMigrations` **纯函数**升级路径表
（两个理由：`:platform:system` 的 JVM 单测无 Robolectric，Android 面本机只编译不执行；
口径写在数据里而不是注释里）。现口径：`upgradeSteps(old, new)` 找不到路径抛
`UnknownMigration` 让升级整体**响亮失败**（与批 78「打不开不回落」同源），降版抛
`IllegalStateException`，**绝不静默重建**。守卫 3 例（无路径抛 / 不静默重建 / 降版抛）。

**验证**：CI 逐字同源 14 测试任务全绿零失败零跳过；facade 201 pass（1 skip = 既有真 addon
环境门禁，`AUTOSCRIPT_TEST_ADDON` 未设）；detekt 全模块绿（修了一处 `UseCheckOrError`：
`throw IllegalStateException` → `error()`）；文档链接门与冻结面门同批跑。

### 2026-10-11 —— 批 96：外审整改第一刀 —— 「排队不挡急停」/jsonl 半行清盘/TTL 截断

**背景**：维护者转来一份外部评审报告（按月度归档记在 `docs/backlog.md`「外审登记」条）。
本次做其中**纯工程、本机可验证**的六件里的四件（B1、B3 半、B4 半）—— 都是
「既在实现的实处、又在测试的实处」的修复；其余两条（`BridgeRouter` 未知异常吞成
`ERR_INVALID_PARAM` 的语义缝、`SqliteKvOps.onUpgrade` 丢表）留给后续批，登记不排期。

**① 排队中的 start 不再挡 stop/killAll/看门狗（外审 B1 高，实测先红）**。
病灶：`RuntimeController.start` 整段持 `guard`，而 `pool.acquire` 在满池时会挂到
`waitTimeoutMillis`（调度链路 60–120s）——「A 在跑、B 排队」时 A 的停止路径全被 B 挡死。
守卫用例（`RuntimeControllerQueuedStartTest`，新建）修前实测：容量 1、A 占用、B 排队时
`stop(A)` 耗时 **2927ms**（= B 的排队超时）。修法两处：
- **Controller**：等证那段移到 `guard` 外（授权决策本就是纯计算），只在记账那一刻取锁；
  新增急停代次 `stopEpoch`（[killAll]/[forceStopAll] 推进），`start` 在 acquire 返回后对表，
  代次已变即 `StartFailed`、**不进在途表**（把一条已被强杀的执行体记在途，等于 stop/killRun
  都当它活着）；
- **池**（`FixedEnginePool`）：es301 不再依赖调用方整段串行化 —— `killAll` 在同一临界区推进
  `stopEpoch` 并强释；`acquire` 在「等完证、夺槽前」与「execute 返回后」两处对表，变了即还证/
  收割并作废（绝不夺被急停强释的槽、绝不 `markRunning` 把账外野进程留在设备上）。
  **边界如实**：exec/调度两路的「A 自然退出、B 立刻拿到空槽」本来就成立（B1 只打急停路径）。

**② jsonl 半行既丢又清盘（外审 B3，实测先红）**。原实现 replay 把无换行尾行在内存里丢掉，
**盘上留着** —— 下一条 append 与残片粘成一行，此后每次重启 replay 都抛 `IOException`，
`tasks.jsonl`/`run-archive.jsonl` **构造即失败**。`FileTaskStore`/`FileRunArchive` 打开时截到
「最后一个完整行」的偏移（`truncateTail`）。守卫各 +1：重开 → **再写一条** → 再重开仍可读
（修前在第三步抛 `IOException: journal 行损坏`）。

**③ 桥请求 TTL 溢出显式截断（外审 B4 半）**。`now + ttl` 对极端正数溢出成负数 = 到期即超时
（对调用方是"立即超时"，还叠着 `expireDue` 收割）。`RequestRegistry` 截到上限
`MAX_TTL_MILLIS`（24h）。守卫 +1：极大 ttl 下期限必须仍在未来且不超过上限。
（另：`FileTaskStore`/`FileRunArchive` 的 `readAllBytes` 全量读、无压缩 —— 属外审「效率」
面，登记未改。）

### 2026-10-11 —— 批 95：T1 杀树换 /proc 实现 —— 修掉批 91 在真机上的静默空转 + 无人点名的 signal

**背景**：批 94 做掉输出流式与取消后，T1 七件欠账剩五件。本批做其中两件（欠账第 4、5 条），
并挖出一个**比记账更严重的实情**：批 91 的 `ProcessHandle.descendants()` 在**真机上从来没
跑起来过**。

**① 实情：`ProcessHandle` 整类不在 android.jar 里（静默空转，不是"有洞"）**。实查
`platforms/android-35/data/api-versions.xml`：无 `java.lang.ProcessHandle` 条目，jar 里也无
class 文件；`java.lang.Process` 桩面只有 destroy/destroyForcibly/exitValue/isAlive/waitFor ——
**既无 `toHandle()` 也无 `pid()`**（javap 逐方法核过）。设备上调用抛
`NoSuchMethodError`/`NoClassDefFoundError`，被批 91 那句 `runCatching { … }.getOrDefault(emptyList())`
吞成**空后代集** —— 杀树退化成只杀主进程，**没有任何报错**。批 91 记账写的「孙子被
reparent 后链断」其实从未成为主要问题：**整条后代链在设备上都不存在**。这与 `Path.of`/
`UnixDomainSocketAddress`/env-NUL 是同一族「纯 JVM 模块、javac 按桌面 JDK 放行、设备上炸
或空转」的坑（本批是该族第四例）。

**② 修法：/proc 扫描 + `kill` 二进制（`ProcOps`/`ProcTreeOps`，新文件）**。三个判据：
- **扫在杀之前**：reparent 只断"死后沿 ppid 往回找"；pid 集合在树还活着时到手，之后谁被
  reparent 都无所谓。
- **同 UID 是继承出来的**：ppid 图上从 rootPid 走得到的集合天然同 UID（fork 不换 uid），
  不必逐 pid 查 status；hidepid=2 还会让别家条目读不到（跳过即可）。
- **按 pid 杀用 `kill` 二进制**（toybox/util-linux 两边都有）—— JVM 没有按 pid 杀的 API。
- **pid 获取两级反射阶梯**（`Process.pid()` 方法 → 私有字段 `pid`）—— 与 `:engine:node-process`
  的 `ProcessLauncher` 同一手法同一理由；都探不到如实回 null（降级只杀主进程，不回 0/自身）。
- **stat 解析找最后一个 `)`**：comm 可变（可带空格与右括号），唯一稳的切法。
- **收尸顺序**（`T1Child.reap` 重写）：扫 → TERM 主+第一波后代 → 宽限（主进程的 waitFor
  即宽限窗）→ 只 KILL 还活着的 → **二次收割**：从仍活着的第一轮成员再扫一轮（宽限期内
  TERM 被忽略的那条新生的后代，父已死时被 reparent，从主进程走不到）→ 还活着的一律 KILL。
  迟到的一波直接 KILL 不再 TERM（宽限窗已过，父马上要被 KILL）。
- **缝**：`T1TreeOps`（生产 `ProcTreeOps`，单测替身）；`ProcOps` 的 procDir 可注入 ——
  合成 /proc 树单测，不借宿主 /proc 判状态。

**③ 无人点名的 signal：按 POSIX 惯例反查（欠账第 5 条的纯 JVM 可解半边）**。exit 帧：
`exitValue >= 128` 且没人点名时，`n = exit - 128` 反查信号名表（1–31；32+ 实时信号各家
不同**不猜**）。这不是编造 —— 128+n 就是「被信号 n 杀死」的编码本身，真 child_process
在这一档报的也是同一个信号名。**已知误报档**：进程自己 `exit(143)` 会被报成 SIGTERM ——
POSIX shell（包括 npm 跑的 `sh`）对同一个数字也是这么报的，脚本生态里正常退出码 < 128。
查不到名字（32+/表外）照旧 `code=128+n, signal=null`。**仍欠**：要区分「自杀 exit(143)」
与「被 SIGTERM」得上 JNI waitid（`WEXITED` 的 `si_status` 区分 `CLD_KILLED`/`CLD_EXITED`）
—— 那是 NDK 件，未排期。

**守卫**：`ProcOpsTest` 7 例（合成 /proc 树：stat 解析含坏行/右括号 comm、ppid 图跨代遍历、
无关树隔离、signalName 表边界）/ `T1ProcessTest` +5（没人点名 128+n 反查、表外不编、
收尸顺序全账 TERM→KILL→二次收割、真进程树：sh 的后台 sleep 孙子 reap 后必须没掉 ——
**这条用例抓到了第一版实现的真 bug**：`readStat` 读成了 `/proc/<pid>` 目录本身而不是它
里面的 `stat` 文件，症状是全部条目 "Is a directory" 被跳过、后代恒空集，与设备上的
静默空转同形 —— 没有这条真进程用例，这个 bug 会原样带到真机上）。完整 CI JVM 门
14 任务全绿。**边界**：真机行为由用户自测；`kill` 二进制在极端 ROM 上的缺席未验
（缺席时静默降级为只杀主进程 —— 与批 91 的行为同界，不更坏）。

### 2026-10-11 —— 批 94：T1 欠账两件 —— 脚本输出真流式 + 命令可取消（桥 kill 帧 + 控制台「停止」）

**背景**：批 91 落了 T1 spawn 桥本体，同批在 backlog 登记了七件欠账；本批做其中纯工程、
本机可验证的两件（③ 输出流式、④ 命令的取消），其余五件（引擎池统一 / CapabilityMask /
无人点名时的 signal / 杀树断链 / 同步三入口与背压）继续挂着。口径见
[`design-decisions.md`](../design-decisions.md) 第 63 项。

**① 输出流式（`ScriptOpExecutor` 补 `OutputSink` 缝，与批 90 `HeavyOpExecutor` 同形）**。
此前脚本 stdout 被 npm 会话进程吞掉、宿主只攢尾部进异常详情 —— 控制台看不到脚本逐行输出。
`NpmScriptExecutor` 的读流线程**边读边报**（空行跳过，批 90 同款），协调器逐行落控制台环。
**「报过流不再重复尾部」的判据挪到了调用方的选型上**：`OutputSink.None` 是调用方显式说
「这边没人看流」—— 那时尾部是失败详情的唯一来源必须兜底；对 None 报了也是空操作，拿
「我们报过」当「已经让人看见了」是撒谎。这与 runHeavy 的 `streamed` 位同理但落点不同
（那条的判据在协调器的 sink 闭包里，这条的在执行体与 `None` 的身份比较上）。

**② 桥侧 kill 帧（`BridgedChild.kill()` 从「只置位」变「真发帧」）**。shim 发
`{t:'kill',id,signal}`，`T1Session` 派发到 `T1Child.kill(signal)`：SIGTERM → `destroy`、
SIGKILL → `destroyForcibly`，**其余信号如实 `ERR_NOT_IMPLEMENTED`**（Java 只有这两种终止
手段，返回 true 却什么都没发生会让调用方以为「杀过了」）。**kill 帧先于 spawn 落地是合法
时序**（shim 发完 spawn 就能发 kill），`T1Child` 用 pending 位兜住「进程还没起」那一档，
`run()` 起完立刻补杀。**exit 帧对宿主确知的杀按真 child_process 口径报**：`code=null` +
`signal=<发出去的信号名>` —— 信号名是确知的事实不是编造；「signal 恒 null」那条旧记账管
的是**没人点名、只看到 128+n** 的情形，那条照旧 null。判据是 `exitValue >= 128`：destroy
与自然退出可以赛跑，先退成 0 的那次按自然退出报。

**③ 控制台「停止」（`cancelConsoleCommand`，按项目停）**。`ScriptOp` 加
`cancelSignal: OpCancelSignal`（读位不是回调：协调器持有的是 `TrackedOp.cancelled` 这个
`@Volatile` 位，读位没有「句柄收走后回调悬挂」的问题）；`NpmScriptExecutor` 的
`waitFor(timeout)` 单发改**切片轮询**（200ms 一片，片间查取消位与墙钟）—— 置位即
`destroyForcibly` + 关会话（桥侧子进程随 `session.close()` 被收），这是「停止」按下去后
进程树**真死**的物理机制；超时路径不变。facade 与 `HostSummary` 各加 `cancelConsoleCommand
(projectId): Boolean`（回「是否取消到了东西」；缺省抛 `ERR_NOT_IMPLEMENTED` 同纪律）；
协调器实现 = 快照该项目未终态句柄逐个走既有 `cancel`（边遍历边摘会漏，故先快照）。
UI：`ConsoleScreen` 跑动中「执行」位换成「停止」（灰着的那段时间用户唯一想按的就是它），
回执措辞「已请求停止」—— 进程回收是异步的，终态行由页面轮询随后拉回来。
**覆盖面如实**：T1 真杀；**重操作（install 会话）仍是「弃结果不杀进程」**（TTL 兜底），
本批没给它接取消探针。

**守卫**：`T1BridgeNodeTest` +1（真 node `sleep 30` + kill → exit 事件
`code=null signal=SIGTERM`）/ `T1BridgeE2ETest` +2（流式到达时间戳：标记须早于返回 1.5s
以上 —— 攒完再报贴近返回时间；取消例：60s 长睡脚本 + 2s 后置位 → 秒级 `ERR_ENGINE_STOPPED`）/
`T1ProcessTest` +4（SIGTERM/SIGKILL 的 destroy 落点、kill 先于 start 的补杀、自然退出不带
信号名）/ `InstallCoordinatorTest` +2（流落环且终态行压其后；`cancelConsoleCommand` 全链：
执行体经取消位观察到、单终态、no-op 回 false）/ `ConsoleCmdOpsTest` +2（停止回执三态、
没选中项目当场拒）。完整 CI JVM 门 14 任务 + detekt（`:ui` baseline 按惯例重生成 ——
`ConsoleScreen`/`InputRow` 加参后签名漂移）+ `lintDebug` 全绿。契约卷同步：§10.3 T1 落地
追记④改写、§10.7 方法表加一行、§10.9 第 3 条加一段（维护者解冻，同批 93 口径）。
**边界**：真机行为由用户自测（abstract 名 socket 上的 kill 帧、停止按钮观感）。

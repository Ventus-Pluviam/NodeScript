### 2026-10-11 —— 批 95：T1 杀树换 /proc 实现 —— 修掉批 91 在真机上的静默空转 + 无人点名的 signal

**背景**：批 94 做掉输出流式与取消后，T1 七件欠账剩五件。本批做其中两件（欠账第 4、5 条），
并挖出一个**比记账更严重的实情**：批 91 的 `ProcessHandle.descendants()` 在**真机上从来没
跑起来过**。

**① 实情：`ProcessHandle` 整类不在 android.jar 里（静默空转，不是"有洞"）**。实查
`platforms/android-35/data/api-versions.xml`：无 `java.lang.ProcessHandle` 条目，jar 里也无
class 文件；`java.lang.Process` 桩面只有 destroy/destroyForcibly/exitValue/isAlive/waitFor ——
**既无 `toHandle()` 也无 `pid()`**（javap 逐方法核过）。设备上调用抛
`NoSuchMethodError`/`NoClassDefFoundError`，被批 91 那句 `runCatching { … }.getOrDefault(emptyList())`
吞成**空后代集** —— 杀树退化成只杀主进程，**没有任何报错**。批 91 记账写的「孙子被
reparent 后链断」其实从未成为主要问题：**整条后代链在设备上都不存在**。这与 `Path.of`/
`UnixDomainSocketAddress`/env-NUL 是同一族「纯 JVM 模块、javac 按桌面 JDK 放行、设备上炸
或空转」的坑（本批是该族第四例）。

**② 修法：/proc 扫描 + `kill` 二进制（`ProcOps`/`ProcTreeOps`，新文件）**。三个判据：
- **扫在杀之前**：reparent 只断"死后沿 ppid 往回找"；pid 集合在树还活着时到手，之后谁被
  reparent 都无所谓。
- **同 UID 是继承出来的**：ppid 图上从 rootPid 走得到的集合天然同 UID（fork 不换 uid），
  不必逐 pid 查 status；hidepid=2 还会让别家条目读不到（跳过即可）。
- **按 pid 杀用 `kill` 二进制**（toybox/util-linux 两边都有）—— JVM 没有按 pid 杀的 API。
- **pid 获取两级反射阶梯**（`Process.pid()` 方法 → 私有字段 `pid`）—— 与 `:engine:node-process`
  的 `ProcessLauncher` 同一手法同一理由；都探不到如实回 null（降级只杀主进程，不回 0/自身）。
- **stat 解析找最后一个 `)`**：comm 可变（可带空格与右括号），唯一稳的切法。
- **收尸顺序**（`T1Child.reap` 重写）：扫 → TERM 主+第一波后代 → 宽限（主进程的 waitFor
  即宽限窗）→ 只 KILL 还活着的 → **二次收割**：从仍活着的第一轮成员再扫一轮（宽限期内
  TERM 被忽略的那条新生的后代，父已死时被 reparent，从主进程走不到）→ 还活着的一律 KILL。
  迟到的一波直接 KILL 不再 TERM（宽限窗已过，父马上要被 KILL）。
- **缝**：`T1TreeOps`（生产 `ProcTreeOps`，单测替身）；`ProcOps` 的 procDir 可注入 ——
  合成 /proc 树单测，不借宿主 /proc 判状态。

**③ 无人点名的 signal：按 POSIX 惯例反查（欠账第 5 条的纯 JVM 可解半边）**。exit 帧：
`exitValue >= 128` 且没人点名时，`n = exit - 128` 反查信号名表（1–31；32+ 实时信号各家
不同**不猜**）。这不是编造 —— 128+n 就是「被信号 n 杀死」的编码本身，真 child_process
在这一档报的也是同一个信号名。**已知误报档**：进程自己 `exit(143)` 会被报成 SIGTERM ——
POSIX shell（包括 npm 跑的 `sh`）对同一个数字也是这么报的，脚本生态里正常退出码 < 128。
查不到名字（32+/表外）照旧 `code=128+n, signal=null`。**仍欠**：要区分「自杀 exit(143)」
与「被 SIGTERM」得上 JNI waitid（`WEXITED` 的 `si_status` 区分 `CLD_KILLED`/`CLD_EXITED`）
—— 那是 NDK 件，未排期。

**守卫**：`ProcOpsTest` 7 例（合成 /proc 树：stat 解析含坏行/右括号 comm、ppid 图跨代遍历、
无关树隔离、signalName 表边界）/ `T1ProcessTest` +5（没人点名 128+n 反查、表外不编、
收尸顺序全账 TERM→KILL→二次收割、真进程树：sh 的后台 sleep 孙子 reap 后必须没掉 ——
**这条用例抓到了第一版实现的真 bug**：`readStat` 读成了 `/proc/<pid>` 目录本身而不是它
里面的 `stat` 文件，症状是全部条目 "Is a directory" 被跳过、后代恒空集，与设备上的
静默空转同形 —— 没有这条真进程用例，这个 bug 会原样带到真机上）。完整 CI JVM 门
14 任务全绿。**边界**：真机行为由用户自测；`kill` 二进制在极端 ROM 上的缺席未验
（缺席时静默降级为只杀主进程 —— 与批 91 的行为同界，不更坏）。

### 2026-10-11 —— 批 94：T1 欠账两件 —— 脚本输出真流式 + 命令可取消（桥 kill 帧 + 控制台「停止」）

**背景**：批 91 落了 T1 spawn 桥本体，同批在 backlog 登记了七件欠账；本批做其中纯工程、
本机可验证的两件（③ 输出流式、④ 命令的取消），其余五件（引擎池统一 / CapabilityMask /
无人点名时的 signal / 杀树断链 / 同步三入口与背压）继续挂着。口径见
[`design-decisions.md`](../design-decisions.md) 第 63 项。

**① 输出流式（`ScriptOpExecutor` 补 `OutputSink` 缝，与批 90 `HeavyOpExecutor` 同形）**。
此前脚本 stdout 被 npm 会话进程吞掉、宿主只攢尾部进异常详情 —— 控制台看不到脚本逐行输出。
`NpmScriptExecutor` 的读流线程**边读边报**（空行跳过，批 90 同款），协调器逐行落控制台环。
**「报过流不再重复尾部」的判据挪到了调用方的选型上**：`OutputSink.None` 是调用方显式说
「这边没人看流」—— 那时尾部是失败详情的唯一来源必须兜底；对 None 报了也是空操作，拿
「我们报过」当「已经让人看见了」是撒谎。这与 runHeavy 的 `streamed` 位同理但落点不同
（那条的判据在协调器的 sink 闭包里，这条的在执行体与 `None` 的身份比较上）。

**② 桥侧 kill 帧（`BridgedChild.kill()` 从「只置位」变「真发帧」）**。shim 发
`{t:'kill',id,signal}`，`T1Session` 派发到 `T1Child.kill(signal)`：SIGTERM → `destroy`、
SIGKILL → `destroyForcibly`，**其余信号如实 `ERR_NOT_IMPLEMENTED`**（Java 只有这两种终止
手段，返回 true 却什么都没发生会让调用方以为「杀过了」）。**kill 帧先于 spawn 落地是合法
时序**（shim 发完 spawn 就能发 kill），`T1Child` 用 pending 位兜住「进程还没起」那一档，
`run()` 起完立刻补杀。**exit 帧对宿主确知的杀按真 child_process 口径报**：`code=null` +
`signal=<发出去的信号名>` —— 信号名是确知的事实不是编造；「signal 恒 null」那条旧记账管
的是**没人点名、只看到 128+n** 的情形，那条照旧 null。判据是 `exitValue >= 128`：destroy
与自然退出可以赛跑，先退成 0 的那次按自然退出报。

**③ 控制台「停止」（`cancelConsoleCommand`，按项目停）**。`ScriptOp` 加
`cancelSignal: OpCancelSignal`（读位不是回调：协调器持有的是 `TrackedOp.cancelled` 这个
`@Volatile` 位，读位没有「句柄收走后回调悬挂」的问题）；`NpmScriptExecutor` 的
`waitFor(timeout)` 单发改**切片轮询**（200ms 一片，片间查取消位与墙钟）—— 置位即
`destroyForcibly` + 关会话（桥侧子进程随 `session.close()` 被收），这是「停止」按下去后
进程树**真死**的物理机制；超时路径不变。facade 与 `HostSummary` 各加 `cancelConsoleCommand
(projectId): Boolean`（回「是否取消到了东西」；缺省抛 `ERR_NOT_IMPLEMENTED` 同纪律）；
协调器实现 = 快照该项目未终态句柄逐个走既有 `cancel`（边遍历边摘会漏，故先快照）。
UI：`ConsoleScreen` 跑动中「执行」位换成「停止」（灰着的那段时间用户唯一想按的就是它），
回执措辞「已请求停止」—— 进程回收是异步的，终态行由页面轮询随后拉回来。
**覆盖面如实**：T1 真杀；**重操作（install 会话）仍是「弃结果不杀进程」**（TTL 兜底），
本批没给它接取消探针。

**守卫**：`T1BridgeNodeTest` +1（真 node `sleep 30` + kill → exit 事件
`code=null signal=SIGTERM`）/ `T1BridgeE2ETest` +2（流式到达时间戳：标记须早于返回 1.5s
以上 —— 攒完再报贴近返回时间；取消例：60s 长睡脚本 + 2s 后置位 → 秒级 `ERR_ENGINE_STOPPED`）/
`T1ProcessTest` +4（SIGTERM/SIGKILL 的 destroy 落点、kill 先于 start 的补杀、自然退出不带
信号名）/ `InstallCoordinatorTest` +2（流落环且终态行压其后；`cancelConsoleCommand` 全链：
执行体经取消位观察到、单终态、no-op 回 false）/ `ConsoleCmdOpsTest` +2（停止回执三态、
没选中项目当场拒）。完整 CI JVM 门 14 任务 + detekt（`:ui` baseline 按惯例重生成 ——
`ConsoleScreen`/`InputRow` 加参后签名漂移）+ `lintDebug` 全绿。契约卷同步：§10.3 T1 落地
追记④改写、§10.7 方法表加一行、§10.9 第 3 条加一段（维护者解冻，同批 93 口径）。
**边界**：真机行为由用户自测（abstract 名 socket 上的 kill 帧、停止按钮观感）。

### 2026-10-11 —— 批 93：控制台 `npm run` / `npx` 拆除人工审批 + env-NUL 缺陷修复（真机实证）

**背景（真机链路先通到门禁前，用户才看清这个门该不该有）**。批 92 修掉 `Path.of` 与
binder 断链后，壳装配干净、控制台命令通道 45–49ms 延迟、回显正常 —— 用户敲 `npm run
hello`，走完审批卡，**卡在 spawn 前的 env 上**（`Invalid environment variable value:
"com.autoscript.t1.xxxx"`，批 92 之后暴露）。用户在依赖面板上亲眼看清审批卡的形态后
裁定：「审批不是这样用的，改一下。依赖面板是方便用户直接安装和管理依赖的地方。你把审批
去掉吧。」—— **本批按该裁定把 `npm run` / `npx` 的人工审批整面拆除，并同批修掉
env-NUL 缺陷**。决策记录见 [`design-decisions.md`](../design-decisions.md) 第 62 项。

**① 审批拆除（逐面列出）**。`ApprovalLedger` / `ApprovalLedgerStore` 及测试删除；
桥面 `requestApprove` / `approvals` 与 JS facade 对应面删除；`:domain` 七个审批类型删除；
`PackageManagerFacade` 的四个审批方法删除（`approvalLedgerSnapshot` 保留**只读**，审计页要
能读旧账）；`HostSummary.resolveNpmApproval` 生产实现删除；UI 审批卡与审批状态删除，依赖
面板回到**纯安装/管理**。放行判据改为解析层白名单（`NpmScriptResolver` 纯 JS bin 白名单、
路径不逃包目录、同名 bin 多包即拒），`versionHash` 仍随 `ScriptOp` 进审计、不再作放行判据
—— 桥面本来就没有 `runScript`/`exec`（脚本到不了宿主执行面），§10.5-2「人机分离」明文仍
保留覆盖脚本自发起那条，收回的只是宿主自己命令行的门。

**② env-NUL 缺陷（真机暴露，桌面绿所以纯 JVM 门看不见）**。根因链：
`AndroidT1SocketBinder.connectTarget = "\0"+name`（abstract 名前缀）→
`NpmT1Bridge.applyEnv` → `AUTOSCRIPT_T1_SOCKET` env → `ProcessBuilder.start()` 见 NUL 抛
`IllegalArgumentException`—— execve 的 envp 以 NUL 结尾，值里带 NUL 无意义。修法：env 给
**裸 abstract 名**，NUL 前缀职责移交 **shim 侧**（`npm-t1-bridge.cjs` 的 `ensureConn`，
判别式与 main.cpp 同源：'/' 前导 = 路径原样直连，否则 = abstract + `'\0'` 前缀）。
桌面 `fileSystemBinder` 路径型 `connectTarget` 原样不动 —— `T1BridgeNodeTest` /
`T1BridgeE2ETest` 继续绿正好钉死「路径直连」分支。

**③ CJS 资源更新后测试首次失败是 ReferenceError**（`connectTarget` 未定义 —— 我第一次把
判别式引用写成 shim 里不存在的变量），**修掉后桥真连**。尝到「资源不是编译对象、改完要么
打包要么测试重放资源」的代价 —— 本批改动全部落在 `src/main/resources` CJS + `:app` 的
binder，`processResources` 已重放，npm/app 两模块测试全绿。

**守卫**：改动全部经 `:app-service:npm:test :app:testDebugUnitTest` 与完整 CI JVM 门
（14 任务）验证，detekt / 文档链接门待推门后由 CI 复核。**边界**：真机行为由用户自测（按
「用户操作设备，我提供 APK」纪律）。

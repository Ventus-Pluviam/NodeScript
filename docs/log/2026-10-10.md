### 2026-10-10 —— 批 91：T1 spawn 桥本体（`npm run` / `npx` 第一次真跑起来）

批 88/89 做的审批卡、批 90 做的流式输出，到这一步之前**全断在同一个地方**：控制台敲
`npm run build`，人工批了审批票，得到的仍是 `ERR_NOT_IMPLEMENTED`（`InstallSeams.kt`
的 `Unavailable` 缺省）。本批把那条链接通 —— **这是 npm P1 里唯一还挡着用户动作的一条**。

**链的形状**（§10.3 T1 下半段）：

```
npm 会话进程（NpmScriptExecutor 起的 node）
  └─ NODE_OPTIONS=--require=<files/.autojs/npm-t1-bridge.cjs>   ← shim（本批新增）
       └─ npm run build → child_process.spawn("sh", ["-c", body])
            └─ shim 把 {cmd,args,opts} 经 unix socket 报给 :main
                 └─ 宿主起真进程，stdout/stderr/退出码经同一条 socket 以「假管道」回填
```

- `npm-t1-bridge.cjs`（classpath 资源）：七个 `child_process` 入口里**只放行异步三兄弟**
  （`spawn`/`exec`/`execFile`）；同步三兄弟与 `fork` 如实 `ERR_NOT_IMPLEMENTED`（同步入口
  要阻塞事件循环等一次 socket 往返，本版做不到）；`detached:true` 当场 `ERR_PERMISSION_DENIED`。
  `BridgedChild` 是宿主侧真进程的**本地投影**（`stdout`/`stderr` 是可读流、`stdin` 可写、
  `pid`/`exitCode`/`kill()` 都在）—— 少一样就是「跑起来了但 npm 收不到输出」。
- `NpmT1Bridge`（宿主侧）：socket 绑定 + 握手（`hello`/`helloAck`/`helloErr`，**帧形状与
  `BridgeHandshake` 刻意逐字同形**）+ 逐帧派发 + 会话关断时按 TERM→宽限→KILL 收全部后代。
- `T1Process.kt`：一个已放行的子进程（起进程、泵两条流、等退出、杀树）。
- `NpmScriptExecutor`：一次 `npm run`/`npx` = 一条 npm 会话进程；`scriptExecutor` 缝从此有值。
- `AndroidT1SocketBinder`（`:app`）：设备侧走 `android.net.LocalServerSocket` + abstract 名
  （JDK 17 的 `UnixDomainSocketAddress.of(Path)` **拒 NUL 前缀**，实测 `InvalidPathException`）。

**两条 shim 互斥**（这是本批最容易做错的一处）：安装会话要的是「零 spawn」（`npm-spawn-gate.cjs`
一律拒），T1 会话要的恰恰是「spawn 走桥」。把门禁 shim 也注进 T1 会话，每一次 spawn 都会先
撞门禁 —— 那不是更安全，是把刚接上的路又堵死。故 `NODE_OPTIONS` 在 T1 这条路上**只注桥那一份**。

**本批最贵的一课（探针测出来的，不是读代码读出来的）**：`Channels.newInputStream(ch)` 与
`Channels.newOutputStream(ch)` **共用同一把锁**（`ch.blockingLock()`），而 `ChannelInputStream.read`
是**抱着那把锁阻塞**的。于是读线程一进 `readLine()` 等下一帧，写线程（子进程输出泵）就永远
拿不到锁 —— 一条**双向**协议被自己的流包装锁成了单向。症状是 `T1BridgeNodeTest` 与
`T1BridgeE2ETest` 双双挂死（探针进程与 JVM 都停在各自的 `read` 上），而 `jstack` 里只有
`BLOCKED (on object monitor)`，**没有一条报错指向锁**，报错面只有「超时」。改用直读
`SocketChannel`（它自己本来就有分开的读/写锁，全双工）后两类的 10 例当场全绿。
同批还修了两处同源的「静默挂死」：握手帧**不能走 `send`**（`send` 排队等 `ready`，而 `ready`
恰恰要等 `helloAck` —— 那条 Ack 永远不会来，实测整条会话挂死）；会话 socket 在**没有在途
子进程时必须 `unref`**（一条常驻 socket 是活跃 handle，会把 Node 事件循环吊住，npm 干完活
永远不退），但子进程在飞时必须 `ref`（退出码是经这条 socket 回来的）—— 判据是「有没有在途
子进程」，写成 `refWhileBusy()`。

**守卫**：`T1BridgeNodeTest` 7 例（真 node，不经 npm：假管道回填 / `exec`+`execFile` /
`detached` 在**脚本进程里**就被拒 / 同步三兄弟与 `fork` 如实不支持 / 缺桥 env 时如实报未接线 /
错凭据被拒 / 连上不发 hello 被看门狗收掉）、`T1BridgeE2ETest` 4 例（真 npm 全链：脚本副作用
落盘 / stdout 回填 / 非零退出的 stderr 进失败详情 / `detached` 在真链上被拒）、
`T1ProcessTest` 5 例（替身：fd 分开 / 双侧各拒一次 / 起不来是结果不是崩溃 / 收尸幂等 /
TERM 不退才 KILL）。**T1 的两类都不设 `assumeTrue`**：`T1BridgeE2ETest` 是全仓**唯一**证明
「npm 真把 spawn 走到桥上」的用例，跳过 = 静默丢覆盖，而它既不在 `TestGuard.ENV_GATED` 里、
也不在 `check-e2e-ran.sh` 的验尸名单里。

**如实记账（这一版没做的）**：**不用引擎池**（§10.3 T1 写的是「沿 EnginePool 同路径拉临时
引擎」，本版起的是 `node <npm-cli.js> run <name>`；引擎池那条路要求「让引擎执行一段 JS」，
而这里要执行的是 npm 自己，spawn 面不同）、**不做最小 CapabilityMask**（脚本进程与 App
同 UID —— 设备上没有可用的隔离手段，沙箱已裁；「最小能力」这一条现在只能靠「宿主只跑它
认得的那条命令」近似）、**不做输出流式**（脚本 stdout 由 npm 自己捕获，宿主只拿摘要）、
**stdin 转发但不做背压**、**`signal` 恒 null**（Java 的 `Process` 不给信号号）、
**杀树的洞**：用 `ProcessHandle.descendants()` 而非 `kill -- -<pgid>`（负 pgid 那条要求子进程
没有自己的进程组，而 `sh -c` 之后的东西是否另起进程组由 shell 与 ROM 决定），代价是**孙子
进程被 reparent 给 init 后链就断了**，本版没兜住。**边界**：真机行为未验（用户自测）。


### 2026-10-10 —— 批 90：控制台「活着」三件（真流式 stdout + 常驻进度推送 + 命令历史落盘）

用户口径是一句体验描述：「控制台从『现取一次』变成『活着』」。落到代码上是三件，
但它们修的是**同一类错**——界面看起来是活的，实际每一步都要人推一下。

**① 真流式 stdout**（`HostNodeExecutor`）。原先 `runNpm` 先 `readBytes()` 再 `waitFor`：
顺序上避开了管道反压，代价是**跑完之后**才拿到全部输出，控制台只显示一大坨。
改成**专门的读流线程**逐行经新的 `OutputSink` 缝报回宿主。缝与 `ProgressSink`
**刻意分开**：那条装的是 `InstallEvent`（**脚本侧的契约形状**，`bridge/js` 的
`onProgress` 逐字对齐），这条装 npm 自己吐的原文 —— 把后者塞进事件契约等于为一个
宿主界面去改脚本侧的面。`line` 是**非挂起**的（读流线程不该为一个 push 让出），
且实现方被要求不抛（真抛了也由读流侧吞掉：界面少显示一行绝不该让安装失败）。
`fun interface` 的抽象方法**不能带缺省值**（Kotlin 编译期就拦）—— 这正好逼每个
实现方显式表态「我报不报流」，写进 KDoc 当特性而不是当坑。
**两处必须记住的**：(a) 流真的报过时**不再补 `outputTail` 行**，否则同一段文本在
控制台出现两遍，用户以为 npm 跑了两回；(b) `OutputSink` **跳过空行** —— 真实 npm
输出以空行结尾，而 `outputTail = output.trim().takeLast(8000)` 在流式模式下取到的是
空行，`HostNodeNpmE2ETest` 就是被这条抓住的（`OUTPUT 行必须是 npm 自己说的那段话（实为「」）`）。

**② 常驻进度推送**（`:ui` 新增 `LivePoll.pollWhile` + 两个调用点）。宿主是
**入队即返回**的，而 `:ui` 的每个读口原先都是「进页面 / 手动刷新时现取一次」——
两者合起来的具体症状有两个：敲完 `npm install axios` 之后 npm 边跑边说的话**一个字都不显示**
（要手动点「刷新」，而那时命令多半已经跑完，那不叫流式，叫事后倒带）；依赖面板的
阶段条**通常只走到 `QUEUED`**（入队那一刻取到的就是它，`DOWNLOAD`/`REIFY` 发生在之后，
没人再取）。现在：提交之后跟到跑完（`runConsoleCmd`/`runPanelCommand`），且子页
**在前台**时一直跟（`MainActivity` 两条 `LaunchedEffect`）。
**为什么是拉不是推**：宿主确实有推送面（`InstallCoordinator.progress` 那条 `SharedFlow`），
但它**没有重放**（`extraBufferCapacity` 是缓冲不是历史），订阅者晚一步就永久丢那一批 ——
而「切进控制台时命令已经跑了一半」正是常态；两个 seq 游标读口本来就是为这件事设计的。
**三条自我约束**（缺一条就把「活着」变成「一直在问」）：**有界**（`maxTicks` 到顶必停，
宿主永远说在跑时界面不能跟着无限轮询）、**只依据宿主给的事实**停（`ConsoleCmdState.running`/
`NpmState.installing`，不是界面自己猜）、**每轮走同一个读口**（两条取数路径迟早会在
「谁先看到新行」上分家）。间隔与轮数**可注入**：单测要验「有界」就得让 `maxTicks` 跑满，
用真实间隔（400ms）会把用例拖成四分钟 —— 一条拖慢整条 CI 的用例迟早被人 `@Disabled` 关掉，
那等于没有这条守卫。

**③ 命令历史落盘**（新增 `ConsoleHistory`，`files/.autojs/console-history.jsonl`）。
原先关掉控制台再进来敲过的就没了，而控制台的用处一半在「把上次那条改一改再跑」。
**与审计史（`InstallHistory`）长得几乎一样但纪律相反**：那个是**审计事实**（只追加、
永不清理，清理策略是 backlog A13，动它会碰 §8.5 的幂等锚点），这个是**便利缓存**
（允许修剪：超阈值整体重写成最近 N 条）。这条差别写在类 KDoc 里 —— **下一个人很容易
把修剪也搬到 `InstallHistory` 上去，那才是真错**。三条口径：**按项目分开读**（控制台的
命令跑在某个项目上，在 A 项目敲的 `npm install axios` 翻到 B 项目去点，落的是 B 的
`node_modules`，而按钮上那行字一模一样；与审计史「读口无参全量」不矛盾 —— 那边问的是
「这个宿主发生过什么」）/ **带凭据形态的行整条不记**（`_auth`/`_password`/`--otp`/
`npm_token`；`npm install --//registry.example.com/:_authToken=…` 是**能敲进控制台的**，
而内存里的环随进程消失、这份历史落盘跨重启还在。**不打码后记录**：打码后的历史看起来
是一条能跑的命令，点它填进输入框得到的是「认证失败」—— 一个由历史自己造出来的假故障；
「这条没进历史」最多少一格便利）/ **写口在 `:ui` 的派发点**（那里才有用户敲的**原文**，
执行入口拿到的是已定形的东西 —— shell 面那条只收得到剥掉入口词的正文，`su id` 记成
`id`，再点一次就会在默认模式里被当成 npm bin 解析）。副作用是「拒收的行与进/退模式
不进历史」变成了**自然结果**而不是特判（那些分支在派发之前就返回了）。

**同批修一处真错（探针测出来的，不是读代码读出来的）**：`InstallCoordinator` 里两处
执行体 sink 调用点写的是 `events.tryEmit(ev)` —— 只喂了 `SharedFlow`，**没经 `emit`**。
而 `emit` 是唯一写三个地方的那个（`installEventRing`/`consoleRing`/`events`），
它自己的 KDoc 写着「全部阶段都经这里」。后果：执行体独有的 `DOWNLOAD`/`REIFY` 阶段
**从未进过事件环**——脚本侧 `onProgress` 收不到它们，阶段条停在 `RESOLVE`。
探针 `SinkRingProbeTest` 打出的 `PROBE-PHASES-IN-RING=[QUEUED, RESOLVE, POST_CHECK]`
是这件事唯一的证据（三个环各自的测试都绿，因为它们都只喂自己那条路）。改成 `emit(ev)` 后
反证会红。探针文件已删。

**守卫与反证**：新增 `HostNodeExecutorStreamTest`（4 例，含**到达时间戳**断言 ——
缓冲实现会在 806ms 时失败而阈值是 300ms，这条是「真流式」与「跑完再报」的唯一区分手段）、
`NpmEventDrainTest` 新增一例（执行体报的阶段必须进环）、`ConsoleHistoryTest`（9 例）、
`LivePollTest`（4 例）、`ConsoleCmdOpsTest` 新增 3 例、`InstallCoordinatorTest` 新增 2 例。
反证三条各自命中并已恢复：把流式回退成缓冲上报 / 把 `emit` 回退成 `events.tryEmit` /
去掉历史的项目过滤与凭据守卫 / 轮询里每轮都读历史。
**验收**：14 任务 JVM 线 + detekt + `lintDebug` + `:app:assembleDebug` 全绿。
**边界**：真机行为未验（由用户自测）；`LivePoll` 的 400ms/600 轮是手感与成本的折中，
真机上是否合适要看实际观感；凭据守卫认的是**参数名形态**不是熵启发式（用户把 token
直接当包名敲不会被认出来 —— 本类是便利缓存不是 DLP，这条边界写在 `looksSecret` 的 KDoc 里）。

### 2026-10-10 —— 批 89：Shizuku 反射面 ↔ R8 keep 对齐门 + 「`input tap` 挂 30s」成因订正（真机实证）

**本批两件**：① 补上 2026-10-10 外审第 2 条要的那道守卫（Issue Two：反射面与
keep 规则靠人工同步，漏一条就是 release 启动闪退）；② 把外审第 1 条的**成因**订正到
真机实证的版本，并留下可复现的对照实验。两件都已并入 `main`（①在 PR #67，②在 PR #66）。

**① 守卫：`ShizukuKeepRuleTest`（`:app`）**。挡的形态是「两条规则分居两个模块，谁都不知道
对方改了没有」—— 反射面在 `:platform:capabilities` 的 `ShizukuInput`，keep 规则在
`:app/proguard-rules.pro`，中间没有任何机械联系。三条判据**双向**：

1. **类名集合相等**：源集里按字符串引用的 Shizuku 类 == keep 规则里保的 Shizuku 类。
   只在 keep = 死规则（保了不再反射的类），只在源 = 反射了没保（release 上静默失效，
   而 debug 不过 R8，**本机全绿**）。
2. **方法 `(名字, 参数表)` 集合相等** —— **参数表是判据的一部分**：2026-10-09 那次真机
   bug 正是「名字对、签名错」（keep 保的是 `waitForTimeout(long, TimeUnit)`，真跑的是
   `(long, String)`），只比名字照样绿。
3. **签名在真类上真解析一遍**（`Class.forName` + `getMethod`）—— 挡「两边一起错」：
   判据 1/2 只证明它们**彼此一致**，不证明它们对。AIDL 接口在 JVM 单测类路径上**真能加载**
   （`dev.rikka.shizuku:aidl` 是传递依赖，实测 `IShizukuService` / `IShizukuService$Stub` /
   `IRemoteProcess` 三件 `Class.forName` 全 OK），所以这条不用真机。

**为什么读源码而不是读常量池**（同模块那条 Shizuku 门读的是字节）：这里要的是
`(名字, 参数表)`，参数表在字节里只剩描述符，与 keep 规则的源码语法对不上，得先反解一遍，
比直接读源码脆。**为什么不把 keep 改成 `{ *; }` 一了百了**：那样判据 2 退化成恒真，
而那张显式方法表本身就是「本应用反射了哪几个方法」的唯一文档 —— 保住表、用门让它自维护，
比删掉表换一个恒真的门强。

**两处必须记住的坑**（都是本门第一次跑出来的）：

- `proguard-rules.pro` 里有一段**注释**逐字引用了 2026-10-09 删掉的那条
  `ShizukuRemoteProcess` 规则。不先剥注释行，它会被当成一条活规则 —— 门第一次跑出来的
  就是这条**假红**（报「保了不再反射的类」）。解析前按 `#` 剥行。
- **`proguard-rules.pro` 必须声明成 `:app:testDebugUnitTest` 的输入**（`app/build.gradle.kts`
  的 `testOptions.unitTests.all { it.inputs.file(...) }`）：Gradle 看不见测试里那次
  `Files.readAllBytes`，不声明则改完 keep 规则该任务照样 `UP-TO-DATE`、门**静默不跑**。
  实测复现过（改 keep 后 `testDebugUnitTest UP-TO-DATE`、测试压根没执行）——
  **一道永远绿的假门比没有门更坏**。

**反证三条**（各自命中，改回即绿）：① `waitForTimeout` 签名改成 `TimeUnit`（名字对、
签名错）；② 整条删掉 `IRemoteProcess` 的 keep（源里还在反射）；③ 源集加一处新反射不保。

**② 订正：「`input tap` 挂 30s」的成因**。2026-10-09 的记账把外审第 1 条（Shizuku 阻塞
调用跑在 `Dispatchers.Main` 上）与「首次 `input tap` 挂 30s」写成**两件各自独立的事**，
并给了「只有冷置后的第 1 条挂」这个特征描述。真机对照实验**两条都推翻**：

- 修复前的构建上，`input tap` 打进**应用自己的窗口**时**每一条都挂**（连续 6 条：
  32.4 / 32.5 / 33.8 / 32.4 / 32.4 / 32.4 s，全部 `超时 30000ms`），不是「只有第 1 条」；
- 机理是**同一件事**：`input` 默认 `INJECT_INPUT_EVENT_MODE_WAIT_FOR_FINISH`，事件投进
  哪个窗口就要等那个窗口处理完 —— 目标窗口属于应用自己时，主线程正卡在
  `IRemoteProcess.waitForTimeout` 上收不了，只好陪等到 30s 超时。目标窗口**不属于本进程**
  时不受影响（`input tap 5 5` 打状态栏，实测 2.6 s 返回）。

**顺带一笔（测量口径，值得记）**：此前报的「`input tap` 延迟 2.4–2.5 s」是**测量工具的成本**，
不是 tap 的成本 —— 那圈循环每次跑 `uiautomator dump`，光它自己就要 ~2.2 s。改成设备侧自带

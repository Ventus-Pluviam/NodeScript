### 2026-10-09 —— 批 87：依赖面板变更半边（§10.9 第 1 条）+ `npm-cache` 尺寸栏（第 5 条）

**起因**：§10.9 第 1 条写的是「已装清单 + 尺寸 + 配额 + **安装输入行 / 旗标 / 阶段进度条**」。
批 81 落了清单那半截，并把「安装输入行/旗标/阶段进度条、依赖树、`hasInstallScript` 前置告警、
白名单放行通道」登记为未落。批 84 把执行体（`InstallCoordinator.runConsoleCommand`）做出来了 ——
于是「没有执行体所以画不了输入行」这条前提**已经不成立**，剩下的是**没人把面板接上去**。
第 5 条的 `npm-cache` 尺寸栏同理：`CacacheIndex.contentBytes()` 批 86 已实现，但没有任何读口。

**做了什么**（五件）：

1. **`:domain`** —— `PackageManagerFacade.cacheStorage()`（新读口，返回
   `NodeModulesStats(projectId = "")`）+ `NpmProjectSnapshot.cache`（每项目快照捎带全机读数）
   + `HostSummary.runNpmPanelCommand(projectId, line)` 与 `HostSummary.npmInstallEvents(projectId,
   sinceSeq, maxBatch)` 两条呈现面读口（都不经桥）。
2. **`:app-service:npm`** —— `InstallCoordinator.cacheStorage()`（量 `content-v2`，走 IO 调度器）
   + `snapshot()` 把缓存读数**提出项目循环外**算一次（全机一份，按项目重算 N 次是白烧 IO）
   + `CacheIndex.contentBytes()`（`fun interface` 的默认体；`CacacheIndex` 覆盖它只累 `content-v2`）。
3. **`:app`** —— `AppShellApplication` 两条生产实现：`runNpmPanelCommand` 直接委托
   `runNpmCommand`（**同一条入口**），`npmInstallEvents` 走 `facade.drainEvents`。
4. **`:ui`** —— 新增 `NpmInstallOps`（`buildInstallCommand`/`buildRemoveCommand`/`submitInstall`/
   `removeInstalled`/`pollInstallEvents`/`foldProgress`）；`NpmState` 六个新字段（草稿、两颗旗标、
   `installing`、`installProgress`、`installSeq`）+ `cacheLabel`/`canInstall` 两条派生；
   `InstallProgressState`（六档阶段 + `ORDER` + `label`）；`NpmScreen` 的 `InstallCard`
   （输入行 + 两颗勾选 + 阶段条）、`QuotaCard` 里多出的 `npm-cache` 一行（与 node_modules
   那行各自独立判空）与清单行上的「卸载」；`MainActivity` 接五条回调，
   `reloadNpm()` 兼作进度续拉。
5. **测试** —— `NpmInstallOpsTest`（22 例：拼装/卸载/超长拒/空输入/无项目/未接线/git 当场拒/三落点/阶段折叠/换项目归零/
   警告不进条/游标只进不退/读失败不抬 opError/现取不抹操作面/`canInstall`/`cacheLabel`/替身响亮失败/
   不串线）+ `CacacheIndexBytesTest`（4 例）+ `InstallCoordinatorTest` 两例（缓存体积进快照、
   缓存不存在读 0 而不是 null）+ `PackageManagerFacadeContractTest` 方法面冻结补 `cacheStorage`。

**五条口径**（写进 §10.9 第 1 条，免得被"统一"掉）：

- **走的是与控制台同一条宿主口**：`HostSummary.runNpmPanelCommand` 委托到同一个
  `InstallCoordinator.runConsoleCommand` —— 同一份判据（`NpmConsoleKeys.parse`）、同一套装前
  多镜像交叉校验、同一道磁盘/配额预检、同一把项目锁与全局安装会话。**门禁强度不取决于用户从
  哪个界面按下去**。新开一条「按 spec 装」的宿主口就是第二份安装入口，而两份入口的差别只在
  「谁先忘了加某道门」上体现出来。卸载同理走 `npm uninstall <name>` 命令通道。
- **进度是阶段不是百分比**：`InstallEvent.Progress.percent` 全仓**从无赋值**
  （`grep -rn 'percent *='` 零命中），`HostNodeExecutor` 起的是 vendored npm CLI 进程、reify 在它
  进程内是黑盒，宿主只在前后发得出三枚粗标记。故画 `InstallEvent.Phase` 六档的**阶段条**。
  §10.9 第 1 条原文那句「job 数」同样拿不到 —— **这条是对原文的收窄，不是实现偷懒**。
- **「离线优先」不是「仅离线」**：旗标拼的是 `--prefer-offline`（先查缓存、缺了仍联网）。
  真正断网也要装上靠的是缓存里恰好有全部闭包（`offlineGap` 答的就是这个）。
- **草稿失败不清**：宿主是先落 ECHO 行**再抛**的（预检/验签拒绝都发生在发出去之后），
  清早了用户看到的是「一句失败 + 一个空输入框」，还得把包名重打一遍。
- **换项目要把阶段条与游标一起归零**（`NpmState.withProject`）：`seq` 是环内全局单调的、
  `drain` 才按 `projectId` 过滤，沿用上一个项目的游标会漏掉新项目 seq 更小的那些事件 ——
  包括 `Finished`，于是阶段条永远停在「进行中」。

**一处收窄的记账**：§10.9 第 1 条的「阶段进度条（packument→下载→解包→链接，job 数）」原文
保留不动（契约不删），收窄理由与替代形态写在同一段下方。

**验证**：14 任务 JVM 线全绿（含新增 28 例）；`detekt` 全模块绿（`ui/detekt-baseline.xml` 随新增
五个 `@Composable` 与 `NpmScreen` 越 `LongParameterList` 线重生成）；`lintDebug` +
`:app:assembleDebug` 绿；`bridge/js` npm test 213（212 通过 / 1 环境门禁跳过）；`gen:wire` 零漂移；
文档链接门 586 条全在；冻结面门通过。

**边界**：真机行为未验（无设备 —— 输入行在软键盘下的观感、阶段条在真安装里走不走得动，随下次
真机冒烟一并看）；进度是**现取**不是常驻轮询（`:ui` 每个读口都是"进页面/手动刷新时现取一次"），
故阶段条通常只走到 `QUEUED` 那一格，点「刷新」续拉 —— 宿主把常驻轮询做出来之前，这是如实的。


### 2026-10-09 —— 批 86：依赖维护四颗按钮 + 缓存按 lock 闭包回收（§10.9 第 5 条动作半边）

**起因**：§10.9 第 5 条写的是「per-project `node_modules` + `npm-cache` 尺寸 + 配额条 →
一键 prune/dedupe/ci 重装/cache clean」。批 81 落了尺寸条那半截，批 85 顺手订正了措辞
（把用户指去控制台敲 `npm prune` —— 那条路是真的通的），但**动作半边一直没有**。
本批补上，并把「cache clean」这颗按钮的语义先拍死：**不是** npm 的 `cache clean`。

**做了什么**（五件 + 一处真错，口径见 [`design-decisions.md`](../design-decisions.md) 第 56 项）：

1. **`:domain`** —— `NpmMaintenanceAction`（`PRUNE`/`DEDUPE`/`CI`）+ `NpmCacheReclaimReport`
   （六字段：`removedEntries`/`removedBytes`/`keptEntries`/`keptBytes`/`keepCount`/`indexRebuilt`）
   + `PackageManagerFacade.reclaimCache()` + `InstallHistoryOp.CACHE_RECLAIM`（`"cache_reclaim"`）。
2. **`:app-service:npm`** —— 新增 `NpmCacheReclaim`：按 lock 闭包回收 content-v2，
   **并摘掉指向已消失 content 的 index-v5 行**；`InstallCoordinator.reclaimCache()` 算保留集
   （**所有项目** lock 闭包的并集，lock 读不出来的项目点名入史）。
3. **`:app`** —— `HostSummary.runNpmMaintenance(projectId, action)` / `reclaimNpmCache()` 两条生产实现。
4. **`:ui`** —— `NpmMaintenanceOps`（`runNpmMaintenanceOp`/`reclaimNpmCacheOp`/`loadNpmSnapshot`）
   + `NpmState` 两个忙碌位（`maintenance` 记住是哪一颗、`reclaimingCache` 单列）
   + `NpmScreen` 的 `MaintenanceCard`（四颗按钮）；配额满那句提示改指本页。
5. **测试** —— `NpmCacheReclaimTest`（12 例：删/留边界、悬空 index 修复、删除标记保留、空账不抛）
   + `InstallCoordinatorTest` 六例（并集保命、`integrity` 为 null 不算保留、读不出的 lock 点名、
   入史明细、悬空 index 顺带修、空账）+ `PackageManagerFacadeContractTest` 三例（方法面冻结补
   `reclaimCache`、报告六字段、枚举三态）+ `NpmMaintenanceOpsTest`（13 例：三落点、回执措辞、
   忙碌位、失败原文透传）。

**同批修的一处真错**：`NpmCacheSeedDeployer.cacheRoot` 成为「npm 的缓存在哪」的**唯一一份**判据。
实测（`grep -rn "npm-cache"`）四处读者各拼各的、**互不相同**：喂给 npm 的 `--cache` 拿到的是
`cacheDir` 本身（少一层）、`CacacheIndex` 读 `cacheDir/npm-cache`、离线 bundle 导入落在第三个目录
（协调器 `npmCacheDir` 未传时的 `projectsRoot` 同级兜底）—— 而 `cacheRoot` 自己当时是**恒等映射**
却挂着「缓存根（cacheDir/npm-cache）」的注释，注释与实现相反。后果不是报错而是**静默失效**：
`offlineGap` 恒报缺口、导入完 `ci --offline` 照样不命中。已全部改走 `cacheRoot`。

**六裁定**：① 按 lock 闭包回收，不是 `npm cache clean`（§10 的离线能力全建在这个缓存上，
全清等于把紧挨着的「按 lock 重装」变成必须联网；用户 2026-10-09 裁定）；② 保留集取**所有项目**
lock 的并集（只看当前项目会毁掉别的项目的离线重装，而用户站在 p1 的页面上看不见 p2 被毁）；
③ 审计 op 名 `cache_reclaim` 不叫 `cache_clean`（名字跟着语义走）；④ **回收必须同时摘掉悬空
index 行** —— 实测 npm 10.9.8：`ci --offline` 走 `byDigest` 不看 index，但**在线**路径读 index，
index 指向已消失 content 时 `npm install` 报 `ENOENT … Invalid response body while trying to fetch`
（不是回源重下），即**悬空 index 让缓存从「没用」变成「有害」且界面上看不出来**；⑤ 认不出形状的
条目一律保留、`deleteIfExists` 失败的不计入 `removed`（删读不懂的文件是「猜」，猜错的代价是别人的
离线能力）；⑥ `CI` 那颗不绕过任何门禁（`facade.ci(offline = true)`，`lockSigner.verifyOrThrow` 照旧先跑）。

**边界（如实划界）**：真机行为未验（无设备）；index 修复的实测证据来自本机 npm 10.9.8（随包 npm
是 12.2.0，桶格式同源但未在该版本复跑）；`cacheDir/npm-cache-seed` **仍无生产部署路径**
（`NpmCacheSeedDeployer.deploy` 零生产调用方，种子素材本身也不存在 —— §10.11 P0 承诺的
「精选缓存种子 + 离线首装」在真机上**一次都没播过种**）；`npm-cache` 尺寸没进配额条；
`ci`/`importOfflineBundle` 是否漏入史**仍未核实**（批 85 登记的那条「同类待查」照旧）。
以上四条均入 [`backlog.md`](../backlog.md)。

### 2026-10-09 —— 批 85：审计页落地（§10.5-2）—— `InstallHistory` 从「生产零消费方」转为有读口

**起因**：§10.5-2 写的是「审计日志（approve/registry 变更/lock 重签）落 App **且可导出**」。
实测复核（`grep -rn InstallHistory --include=*.kt` 去掉测试与定义处 = 零命中）发现前半截成立、
后半截不成立，而且问题比「导出没做」更靠前：**读口压根不存在**。用户点过的每一次批准、
每一次镜像源变更、每一次失败安装都落在 `files/.autojs/install-history.jsonl` 上，
而界面上一个字也看不到。

**做了什么**（五件，口径见 [`design-decisions.md`](../design-decisions.md) 第 55 项）：

1. **`:domain`** —— `InstallHistoryEntry`（五字段：`op`/`projectId`/`success`/`detail`/`atMillis`，
   **由落盘格式决定**，不由界面想显示什么决定）+ `InstallHistoryOp`（已知操作名的**唯一一份**）
   + `PackageManagerFacade.history()`。
2. **`:app-service:npm`** —— `InstallCoordinator.history()` 实现（`history?.all()` 投影；
   未注入时回空表，与写侧 `history?.record(...)` 的静默可空同一条语义）；
   `InstallHistory.Op` 改为指向 `:domain` 那份的**别名**（`:ui` 看不见本模块）；
   **补记 `enqueueHeavy` 的磁盘/配额预检拒绝**（原先不入史）。
3. **`:app`** —— `HostSummary.npmHistory()` 生产实现（读装配产物里那个 facade，未接线**抛**）。
4. **`:ui`** —— `AuditScreen`/`AuditState`/`AuditOps`，入口在**依赖管理页顶栏**那颗「审计」。
5. **契约测试** —— `PackageManagerFacadeContractTest` 的方法面冻结补上 `history`；
   新增两条：五字段形状、以及「未知 op 能构造出来 + 已知名八个逐字钉住」。

**三条呈现口径**：失败行不藏（审计要能回答「用户当时看到成功了吗」）/ 未知 op 原样显示
（不编「未知操作」）/ 筛选只影响显示（宿主读口**无参**全量 —— 按项目筛会让 `registry` 那条
`projectId` 空串的全局变更掉出去，而它恰恰是审计最该看见的）。

**顺手改的一处措辞**：依赖管理页配额满那句原写「先 prune 或删掉不用的包」，而 prune 的按钮
**不在本页** —— 改成「去控制台敲 `npm prune`」（批 84 的白名单里真有 `prune`，那条路是通的）。
把用户指去一个真能做成事的地方，比一句含糊的建议好。

**验收**（本机，CI 同源命令）：

- 14 任务 JVM 线（ci.yml 那条，含 `:platform:editor:testDebugUnitTest`）**全绿**；
- `./gradlew detekt` 全模块绿（`ui/detekt-baseline.xml` 随新增 `@Composable`、
  `MainActivity.onCreate` 复杂度 32、`ManagementSubPageHost` 函数名重生成）；
- `lintDebug` + `:app:assembleDebug` 绿；
- 新增用例：`:domain` 契约 2 条、`:app-service:npm` 3 条（写入序 + 全局变更不掉队、
  失败两条路都留痕、未注入 history 回空表）、`:ui` 8 条（`AuditStateTest`）。

**边界（如实划）**：§10.5-2 的「**可导出**」那半截**未落** —— SAF 选目录 + 写文件那条通道没接，
故界面上**不画导出按钮**；真机行为未验（无设备，按既定纪律不连 adb 自测）。

**顺带修的一条测试自身的问题**：新加的两条用例最初共用 `newHistory()`（同一个
`.autojs/install-history.jsonl`），第二条读到了第一条写的行 —— 改成各自一本账
（`.autojs-boom` / `.autojs-gate`）。这不是产品 bug，但**共用一本账的测试会随执行顺序变绿变红**，
那是最难查的一类假绿。

### 2026-10-09 —— 批 84：控制台改做命令面（§10.9 第 3 条）+ 日志整体搬去「日志管理」

**用户口径（逐字）**：「控制台不是放系统日志的地方，是用来执行命令的，比如 npm。或者装的一些依赖会有命令」。
控制台页当时全是 §7.3 那条 `HostSummary.console` 读口的呈现（宿主行 + 脚本 console 行 + 在途执行块），
与批 70 新建的「日志管理」页职责重叠 —— 第 40 项当时把控制台记成「不动（现在不知道干啥用）」。

**五个提交**：

1. `feat(domain)` —— `NpmConsoleKeys`（命令行的**唯一一份**判据：`parse` 四形态 / `SUBCOMMANDS` 白名单 /
   `HEAVY_SUBCOMMANDS`/`LIGHT_SUBCOMMANDS` / `packageSpecsIn` / `gitSpecIn` / `rejectProjectId`）
   + `PackageManagerFacade.runConsoleCommand`/`consoleOutput`（缺省抛 `ERR_NOT_IMPLEMENTED` / 空快照）
   + 四个 DTO（`NpmConsoleHandle`/`NpmConsoleSnapshot`/`SequencedConsoleLine`/`NpmConsoleLine`）
   + 枚举 `NpmConsoleLineKind`；`HostSummary` 两条缺省读口；`ScriptPaths.PROJECT_ID` 收掉 `.`。
2. `feat(npm)` —— `InstallCoordinator.runConsoleCommand`（解析 → **先落 ECHO 行** → 派发；
   轻操作同步现取、重操作 `enqueueHeavy`、`run`/`npx` 走 T1 门禁）+ `consoleOutput`
   （第二条 `SeqRing<NpmConsoleLine>`，512，`running` 判据是**句柄账**）+ `HeavyOpOutcome.outputTail`
   （`HostNodeExecutor` 截尾，`OUTPUT_TAIL_CHARS`）+ `InstallEvent` → `NpmConsoleLine` 投影一处。
3. `feat(app)` —— `HostSummary.runNpmCommand`/`consoleOutput` 接上装配产物；`FakeHost` 两条响亮失败。
4. `feat(domain)` —— `NpmConsoleLine.ok` 成败位（失败标红不靠文本猜）+ 审批被拒话术指向**真的那一页**
   （管理面板 → 依赖管理，原先写「能力中心的审批卡」是批 81 之前的位置）。
5. `feat(ui)` —— 控制台重写成命令面（`ConsoleCmdState`/`ConsoleCmdOps`/`ConsoleScreen`：项目选择 +
   输入行 + 输出列表 + 自动滚底 + `pageFull`/`gap` 如实标注）+ `LogManagementScreen` 三段化
   （系统日志 / 脚本输出（含在途执行块 + 「停止」）/ 任务日志）+ `ConsoleState.systemLogLines()`/
   `scriptOutputLines()` + `ActiveRunState.summaryText()` 收拢两屏重复。

**六裁定**（详见 [`design-decisions.md`](../design-decisions.md) 第 54 项）：

1. **日志搬去日志管理，一行不少** —— 数据面（`ConsoleCollector`/游标语义/`stopRun`/`ConsoleSnapshot`）
   **一个字没动**，搬的是 `:ui` 的消费方；`TaskCenterScreen` 的在途块原样保留。日志管理从此三段
   （用户 2026-10-09 裁定「三个钮」）。
2. **只认 npm 与 npx，不加 sh**（用户口径「不用加 sh 啊」）—— 本仓没有 shell，任意命令走脚本侧的
   `auto.shell` 桥面，那是**另一个面**。
3. **子命令白名单** `install/uninstall/ci/ls/list/prune/dedupe/audit` —— 不是黑名单（npm 60+ 子命令，
   黑名单漏一个就是一条没人守的路）。
4. **输出粒度 = 事件流 + npm 输出尾部**（用户裁定，否掉「新开真流式 stdout 事件」那案）——
   **不新开桥面事件**，脚本侧契约不因宿主多了一个界面而改形状。**真流式 stdout 未落**。
5. **依赖提供的命令照实接线**（用户裁定「照实接线」）—— `npm run`/`npx` 走 T1 门禁：
   未获批 → `ERR_PERMISSION_DENIED` 且请求已入队；获批但 spawn 桥未接 → `ERR_NOT_IMPLEMENTED`。
   **审批 ≠ 执行**：门禁只入队不排队命令，批完要**重敲那一行**。
6. **判据唯一一份住 `:domain`** —— 宿主侧执行入口与 `:ui` 输入行读同一个结论（界面放行、宿主拒绝
   是最坏的漂移方向：用户看到「执行失败」而不是「你这行写错了」）。

**门禁强度不取决于入口**：控制台敲 `npm install axios` 与依赖面板装同一个包走**同一套**装前多镜像
交叉校验（§10.5-1）、磁盘预检/配额/项目锁/全局安装会话。入史那一栏只记**子命令**而非完整 argv
（用户手敲的 argv 可能夹着凭据形态的参数，审计表长期留存）。

**同批修一条判据错**：`ScriptPaths.PROJECT_ID` 原放行 `.`，于是 `a.b` 合法、`..` 也合法 ——
而 `projectsRoot.resolve("..")` 正好**跳出项目根**（那条 `require` 自称「防路径逃逸」，
实际把最经典的一种逃逸放行了）。收掉 `.`，`NpmConsoleKeys.rejectProjectId` 的话术跟着改。

**未落 / 边界**：真流式 stdout、shell 引号解析、命令历史持久化（不落盘）、白名单外子命令
（`config`/`publish`）、T1 spawn 桥本体（`scriptExecutor` 仍缺）、命令的**取消**
（`NpmConsoleHandle` 与 `InstallHandle` 刻意分开，故没有 `cancel()`）；真机行为未验（无设备）。

- **断链 1 —— 生产环境的 `--registry` 永远指向官方**：`HostNodeExecutor.registry` 缺省
  `NpmRegistryVerifier.OFFICIAL` 并写进 argv，而**全仓唯一的构造点** `AppShellKit.wireNpmExecutor`
  **从不传这个参数** → 用户经 `auto.npm.setRegistry(...)` 设的镜像对真实安装**毫无影响**，
  npm 每次都被 `--registry` 强制钉在官方源上。
- **断链 2 —— 项目 `.npmrc` 根本没被 npm 读到**：`prepareWorkDir` 只拷 `package.json`/
  `package-lock.json`，**不拷 `.npmrc`**；而 `runNpm` 用 `--prefix workDir`。

  本机用 **npm 12.2.0**（与仓里 vendored 同版本，`node-runtime-build/VERSIONS.env`）实测：

  | 场景 | 生效 registry |
  |---|---|
  | cwd 有 `.npmrc`、`--prefix` 指向别处 | **`--prefix` 那个目录的 `.npmrc`**（cwd 的被忽略） |
  | cwd 有 `.npmrc`、不给 `--prefix` | cwd 的 `.npmrc` |
  | 都不给 | 出厂官方 |
  | `--registry` 显式给出 | 赢 `.npmrc` 的 `registry=` 键（但文件仍被读，`@scope:registry` 等键照常生效） |

  生产两处都不满足 → 项目 `.npmrc` 是**死配置**。

- **两条的净效果**：`setRegistry` / `config()` 的写入侧（`NpmBridgeHandler` → `InstallCoordinator.config`）
  **生产上是空转**。唯一真读项目 `.npmrc` 的是交叉校验的 `readRegistryFromNpmrc` —— 于是
  **校验的首选**与**实际安装的那家**可以不是同一家。本批的修法：`resolveRegistry` 成为唯一读数点，
  既喂交叉校验的 primary、也决定实际安装（`--registry` 不再无条件注入，改由 `--userconfig` +
  拷进 workDir 的项目 `.npmrc` 表达）。

- **全局一份，不做按项目覆盖**（用户口径就是全局）；
- **每次 spawn 现读**（`() -> Map` 而不是装配期定死的 `Map`）：改完**下次执行即生效**，不必重启 App。

- **不注入 npm 安装会话进程**：`HostNodeExecutor` spawn 的 npm CLI 是宿主工具进程、不是用户脚本，

### 2026-10-09 —— 批 81：依赖面板 + 审批卡（§10.9.1 / §10.9.2）—— 审批链从此有生产落点

§10.9 第 1/2 条（依赖面板、审批卡）在契约里是 P0，`design-status.md` 与 §11.3 第 6 条把它记成
「UI 未排期」。本批先做了一次实测复核，结论是**不是排期问题，是结构问题**：

- `PackageManagerFacade.resolveApproval` 与 `pendingApprovals` **全仓零生产调用方**（只有测试调），
  `ApprovalLedger()` 的 `store` 缺省 `null` —— 于是：审批票永远停在 PENDING、
  `runScript`/`exec` 永远过不了那道闸（T1 面等于纸面存在），重启后 `requestId` 还从 `apr-1` 重来、
  与历史票碰撞（`resolve` 按 requestId 查表，新旧账就此串在一起）；
- `NpmShellKit.assembleHandler` 建 `ApprovalLedger()` 时**没传 store** —— 已实现且已单测的
  `FileApprovalStore`（`files/.autojs/approve-ledger.jsonl`）**零生产调用方**；
- 管理面板的「依赖管理」是 toast 占位，而底下 14 个桥方法 + `storage()` + 审批入队口**都在**。

**三个提交**（每个一个逻辑完成点）：

1. `fix(npm)`：`NpmShellKit` 的 `approvalStore` 缺省改成 `FileApprovalStore(filesDir/.autojs)`
   —— 生产路径**不该**传 null，逃生口（`approvalStore = null`）保留但显式。两条新单测：
   缺省落盘（`requestApprove` 后 `approve-ledger.jsonl` 真在盘上、含 `"op":"submit"`）、
   显式不落盘（盘上零文件）。顺带订正 `ApprovalLedger`/`FileApprovalStore` 的 KDoc：
   真实文件名是 `.jsonl`，§10.2 正文里那处 `approve-ledger.json` 是过期写法。
2. `feat(domain,npm)`：读口 —— `PackageManagerFacade.snapshot(): NpmPanelSnapshot`
   （`projects` 按项目号排序 + `pendingApprovals` **全局**队列）+ `HostSummary.npmSnapshot()` /
   `resolveNpmApproval()` + `AppShellApplication` 两条实现 + `AssembledShell.npmFacade` 字段。
   读口**不经桥**（桥面是脚本侧的面，依赖面板是宿主自己的界面），桥面方法表**一条不加**。
3. `feat(ui,npm)`：`NpmScreen`（管理面板 → 依赖管理，两个分段：已装依赖 / 待审批）
   + `NpmState`（纯数据，JVM 可测）+ `MainActivity` 的 `reloadNpm`/`decideApprovalOp`。

**为什么读口是「全量一次现取」而不是「按项目问一次」**（本批中途改过一次口径，值得记）：
初版做成 `npmSnapshot(projectId)`、把 `pendingApprovals` 挂在项目上。随即发现两个问题 ——
① 审批队列在数据上**没有项目维度**（`resolveApproval` 不带 projectId、`ledger.all()` 是全局的），
按项目筛会让用户**漏掉别的项目上等着的那张卡**，那正是本批要修的缺陷本身；② 按项目问 N 次 =
N 次目录遍历 + N 套「读失败该怎么办」的分叉。改成全量后，项目列表取 `storage()` 的键
（项目根下的目录）而不是 lockfile 的键：装了依赖但还没落 lock 的项目也有一棵 `node_modules` 要管。

**命名**：`:domain` 的快照 DTO 叫 `NpmPanelSnapshot` 而**不是** `NpmSnapshot` ——
`app-service/npm` 里已有一个 `NpmSnapshot`（§10.9.4 高信任快照导出/验签的执行体），
两个同名类在 `InstallCoordinator` 里 import 撞车（编译期实测撞了）。名字先到先得，后者改名。

**呈现面刻意不做的三件事**（做了就是撒谎，理由写在 `NpmScreen` 的文件头 KDoc）：
不画安装输入行/进度条（读口只到"看"这一层，画一个按下去必失败的框比不画更糟）、
不画依赖树（`list(depth)` 宿主侧只用 0，画树就是把平铺清单伪装成树）、
不画 0% 配额条（尺寸没量到时显示「未量到」，0% 是在说"这个项目不占地方"）。

**顺带的结构整理**（不是洁癖，`onCreate` 已贴着 detekt 的 `LongMethod` 线 120）：
项目页与三个管理子屏抽成 `ProjectTab` / `ManagementSubPageHost`；三个子页开关收成一个
`ManagementPage?` —— 路由、返回键让位、切页现取**三处同序**（控制台 → 依赖 → 日志）；
`TabReloadEffect` 从"把开着的都读一遍"改成**按在前台的那一个**现取（依赖面板要遍历
`node_modules` 算尺寸，在别的子页上白跑是真金白银的 IO）。

**验收（本机）**：`:domain:test`、`:app-service:npm:test`、`:ui:testDebugUnitTest`、
`:app:testDebugUnitTest` 全绿（含新增 `NpmStateTest` 9 例）；`:domain`/`:app-service:npm`/`:ui`/`:app`
四模块 detekt 绿（`ui`/`app` 的 baseline 随新增的 `@Composable` 与 `AssembledShell` 构造参数同步重生成）。
**边界**：真机行为未验（无设备）；`NpmScreen` 的**安装**半边（输入行/进度条/依赖树）**未落**，
本次只落"看"与"批"两条。

### 2026-10-09 —— 批 80：`child_process` 拦截 shim 接线 + 零 spawn 金标准（§10.11 P0 / §10.12 末行）

§10.11 P0 与 §10.12 末行一直把「安装会话强制注入 child_process 拦截 shim」写成 P0 承诺，并给了
CI 金标准（child_process 替换为 throw 的 harness 里跑全命令矩阵必须全绿）。它此前**一直未落**：
`--ignore-scripts` 只挡 lifecycle 脚本（版本无关，见 §10.12），挡不住**非脚本** spawn —— npm 自己
新增一条 `execFile` 路径、或某个包在 `bin/` 里直接 `require('child_process')`。那类漂移在本平台上
的表现是**静默失败**（装完了但东西不对，无人报错）。本批把它变成可判定的不变量。

**新增三件（`:app-service:npm`）**：

- **`src/main/resources/com/autoscript/appservice/npm/npm-spawn-gate.cjs`** —— shim 本体。
  七个入口（`spawn`/`spawnSync`/`exec`/`execSync`/`execFile`/`execFileSync`/`fork`）全替换为抛错：
  非批准 spawn → `ERR_NPM_SPAWN_BLOCKED`；`detached:true` → `ERR_PERMISSION_DENIED`
  （§10.3 T1 明写「shim 直接拒绝 detached/setsid」：脱离进程组的子进程回收不到）；`fork` →
  `ERR_NOT_IMPLEMENTED`（§10.3「明确不可行」）。错误**必须带 `.code`**（Node 的错误折叠面认它，
  普通 Error 会被折成 `ERR_INVALID_PARAM` = 把「被门禁拦了」说成「参数错了」），并往 stderr 打一条
  `[npm-spawn-gate] <CODE>: <detail>` 播报（`redirectErrorStream` 后是唯一能到宿主的通道）。
- **`NpmSpawnGate`** —— 落位 + 注入串 + 播报解析。shim 住 classpath 资源、落到
  `filesDir/.autojs/`（**不随 npm 素材树**：素材树受 `npm-manifest.json` 逐件摘要对账，
  塞宿主自己的文件会让「清单与 APK 文件集合不一致」每次启动必红）；`mergeNodeOptions` 把
  `--require=<落点>` **追加**进已有的 `NODE_OPTIONS`（不覆盖父环境里那份别人的设置）；
  `blockedIn` 从合并输出里取**最后一条**播报（npm 重试时杀死会话的那次才是病因）；
  `errorCodeOf` 把播报码折成领域错误码，认不出的折回 `ERR_NPM_SPAWN_BLOCKED`。
- **`HostNodeExecutor` 新增 `spawnGateFile`**：非 null 时注入 `NODE_OPTIONS`，非零退出时
  **门禁播报优先于「退出码 N」**（被拦时 npm 只笼统报一句失败，真病因是 shim 那条）。

**装配层 fail closed**：`AppShellKit.wireNpmExecutor`（自 `assemble` 外迁的 60 行，装配根已经三十几个
参数）把「素材落位 + 有 Node 宿主 + shim 落位」三条串起来 —— **任一不成立就保持
`HeavyOpExecutor.Unavailable`**。shim 落位失败**不注入执行体**：它是 P0 承诺面，静默降级成
「装是能装、守卫没了」正是那条风险本身。原因原文进 `npmCliFailure`，不吞。缺省资源永远在
classpath 上，故这条分支由新增的 `npmGateDeploy` 注入缝在测试里够到；`AssembledShell` 新增
`npmSpawnGate` 字段（非 null = 守卫在盘上）。

**零 spawn 金标准落成 `NpmSpawnGateMatrixTest`**（§10.12 末行那条要求的落地）：① 门禁注入下
install/ls/dedupe/prune/uninstall/ci 全绿且零播报；② 同一条矩阵**不注入也全绿**（反向变异：
少了它「全绿」可能只是矩阵本来就没跑起来）；③ `npm run <script>` 在门禁下确实被拦 ——
判据是**产物文件在不在**（脚本正文会回显在 npm 输出里，拿词表判会自己骗自己），并先证明无门禁时
该脚本真跑过。只用本地 `file:` 依赖（零网络），故能进 PR 门；已登记进
[`check-e2e-ran.sh`](../../.github/scripts/check-e2e-ran.sh) 的 nightly 验尸清单
（本机没 npm 时跳过是对的，CI 上恒真跑）。

**验证**：本机 14 任务 JVM 线全绿；`NpmSpawnGateTest` 9 例（含两例**真起 node** 验七个入口 +
一例反向证明拦住它的是 shim 不是环境 + 两例执行体注入）与 `NpmSpawnGateMatrixTest` 3 例全过；
去掉 `-PskipNpmE2E` 跑 `check-e2e-ran.sh` **四条真 npm 路径全部 ✓**；`lintDebug` + `assembleDebug` 绿，
`npm-spawn-gate.cjs` 实测进了 APK（`unzip -l` 可见，4799 字节）。

**边界（写死，别当它是沙箱）**：本 shim 是**不变量守卫**，不是安全边界 —— 已获批的脚本可以
`delete require.cache[require.resolve('child_process')]` 后重新 require 拿到未打补丁的模块。
真正的对抗面是审批（§10.5-2 人机分离）与 T1 会话的最小 CapabilityMask（§10.5-4）。
口径见 [`design-decisions.md`](../design-decisions.md) 第 50 项。

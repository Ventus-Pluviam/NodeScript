### 2026-10-09 —— 批 83：镜像源管理（§10.9 新增第 8 条）+ registry 两条断链收口

管理面板四项入口只剩「镜像源管理」还是 `toast?.show("镜像源管理尚未开放")`。backlog 批 82 那条追记
明确要求**先裁归属，别照抄「环境变量」的形状**（那是脚本面，这是 npm 面）。探查时发现两条**比 UI 占位
更严重**的断链，本批一并收口。

**归属与粒度**：管理面板的「镜像源管理」= **npm registry 的全局配置面**，归 `:app-service:npm`
（它本来就在管这件事：`NpmConfigKey.REGISTRY`、项目 `.npmrc` 写入口 `config()`、
`InstallHistory.Op.REGISTRY` 审计键、交叉校验首选）。**粒度 = 全局一份**（用户 2026-10-09 裁定），
对应 §10.2 三层链的 `files/.npmrc`(userconfig) 那一层 —— **该层此前零实现**（全仓只有
`NpmProjectLayout.npmrc(projectId)` 一个路径函数）。否掉的两案：只做项目级（用户要的是"一次改完
所有项目"）、全局缺省 + 项目覆盖的编辑面（项目那层仍可手编 `.npmrc`，界面代管它就要处理
"项目覆盖了全局"的显示歧义，收益不抵成本）。

**本批真正的交付物是一条链**：解析链两层 —— **项目 `.npmrc` → 全局 `files/.npmrc` → 出厂官方**，
落在 `InstallCoordinator.resolveRegistry` 一处，**交叉校验的首选与安装实际用的那家取同一个值**。
UI 只是这条链的呈现面。

**四个提交**：

1. `feat(domain)`：判据与契约 —— `NpmRegistryKeys`（`canonicalize` 规整化 / `reject` 拒收原文，
   判据的**唯一一份**，与批 82 的 `ScriptEnvKeys` 同形）。`NpmRegistryVerifier.canonicalRegistry`
   改为**委托**它、`OFFICIAL`/`MIRROR` 改为指向它的**别名** —— URL 字面量从此只有一份。
   顺带修掉一个潜伏 bug：`canonicalRegistry` 只 `catch IllegalArgumentException`，
   而 `URI()` 对畸形输入抛的是**受检的** `URISyntaxException` —— 该路径此前只在畸形输入下可达。
   `:domain` 此前零 `java.net` 用法，本批是**第一处**（只做形态判定，不涉 IO，不触 `ArchitectureTest` 禁令面）。
   另加 `NpmRegistrySnapshot`（`configured`/`defaultRegistry`/`secondaryRegistry`）+
   `PackageManagerFacade.globalRegistry()`/`setGlobalRegistry()` 两条带缺省实现的方法（老替身零改动）+
   `NpmPanelSnapshot.registry` 字段（带缺省值，13 处构造点零改动）。
2. `feat(npm)`：落盘与两层链 —— `NpmrcFile`（`readKey` 取**最后一行**，与 npm 同口径；`writeKey`
   **整文件重写**：`removeIf` 后追加，`null` = 删键）+ `NpmGlobalConfig`（`files/.npmrc`）+
   `InstallCoordinator` 的 `globalConfig` 参数与 `resolveRegistry` 两层链 + `globalRegistry()`/
   `setGlobalRegistry()`。**三条写法裁定**：写入侧**存原样（只 trim）不规整化** —— 规整化会丢 query，
   自建网关用 `?token=…` 的凭据会被静默剥掉（表现为"保存成功"之后永久 401）；**空输入 = 删键**
   （恢复出厂，不是写一个空值行 —— 后者让 npm 拿到空 registry 而每次安装都失败）；**校验不过抛原文**。
   审计行 `projectId` 传**空串**（全局变更没有项目；改 `InstallHistory` 行格式会动审计契约）。
3. `fix(npm)`：`HostNodeExecutor` 断链收口 —— 构造参数 `registry: String` 改成
   `registryOverride: String? = null`（null = **不注入** `--registry`），新增 `userConfig: Path?`
   （非 null 时 argv 加 `--userconfig`），`prepareWorkDir` 开始**把项目 `.npmrc` 拷进 workDir**，
   argv 构造提成 **public 纯函数 `npmArgv`**（现在内联在 `runNpm` 里且类一构造就 `require` 素材文件，
   导致"`--registry` 该不该出现"这条不变量**零 node、零文件系统**也钉不住；public 而非 internal 是因为
   Kotlin `internal` **跨模块不可见**，而 `:app` 的装配测试正是它最重要的消费方）。
   `AppShellKit` 的 `NpmWiring`/`wireNpmExecutor` 改 `internal`（让 `:app` 测试能真走到生产装配那条路），
   构造点补 `userConfig = filesDir.resolve(".npmrc")`。
4. `feat(ui)`：呈现面 —— `:app` `HostSummary.npmRegistry()`/`setNpmRegistry()` 两条 +
   `AppShellApplication` 实现（读口**不经桥**，与依赖面板/审批卡同一条纪律）；
   `:ui` `RegistryState`（纯数据，`LoadState` + `snapshot` + 两条账分开的 `loadError`/`opError` +
   `draft`；`validate` 调 `:domain` 的同一个 `reject`，不自己判 URL）+ `RegistryOps`（三个顶层
   `internal suspend` 函数，搬出 Activity 是因为它贴着 detekt `TooManyFunctions` 线，且顶层能用
   `FakeHost` 直接测）+ `RegistryScreen`（当前生效值 + 出厂缺省说明 + 输入行 + 保存/恢复出厂 +
   交叉校验第二意见一句说明）。**刻意不画**镜像列表/一键切换 —— 那要 §10.9 第 6 条的首启引导
   （ping 探测 + 候选表），画一个按下去只是填输入框的"快捷按钮"是在假装探测过。
   `MainActivity` 四处同序改齐（`subPage` 计算 / `ManagementSubPageHost` / `ManagementBackHandler` /
   `TabReloadEffect` 分派），顺手把 `ManagementBackHandler` 里那条 `else -> closeLogManagement()`
   改成显式枚举分支 —— 留 `else` 会在加新子页时**静默吞掉返回键**（新页按返回 = 把日志管理关了，
   而不是关自己）。`ManagementScreen` 那一行接上真入口、KDoc 更新（四项入口全部落地，不再有占位）。

**两条断链（实测证据，这是本批比 UI 占位更值得留的东西）**：

- **断链 1 —— 生产环境的 `--registry` 永远指向官方**：`HostNodeExecutor.registry` 缺省
  `NpmRegistryVerifier.OFFICIAL` 并写进 argv，而**全仓唯一的构造点** `AppShellKit.wireNpmExecutor`
  **从不传这个参数** → 用户经 `auto.npm.setRegistry(...)` 设的镜像对真实安装**毫无影响**，
  npm 每次都被 `--registry` 强制钉在官方源上。
- **断链 2 —— 项目 `.npmrc` 根本没被 npm 读到**：`prepareWorkDir` 只拷 `package.json`/
  `package-lock.json`，**不拷 `.npmrc`**；而 `runNpm` 用 `--prefix workDir`。

  本机用 **npm 12.2.0**（与仓里 vendored 同版本，`node-runtime-build/VERSIONS.env`）实测：

  | 场景 | 生效 registry |
  |---|---|
  | cwd 有 `.npmrc`、`--prefix` 指向别处 | **`--prefix` 那个目录的 `.npmrc`**（cwd 的被忽略） |
  | cwd 有 `.npmrc`、不给 `--prefix` | cwd 的 `.npmrc` |
  | 都不给 | 出厂官方 |
  | `--registry` 显式给出 | 赢 `.npmrc` 的 `registry=` 键（但文件仍被读，`@scope:registry` 等键照常生效） |

  即 **`--prefix` 一旦给出，npm 的项目级配置就只看 `prefix/.npmrc`**，cwd 不再参与。
  生产两处都不满足 → 项目 `.npmrc` 是**死配置**。

- **两条的净效果**：`setRegistry` / `config()` 的写入侧（`NpmBridgeHandler` → `InstallCoordinator.config`）
  **生产上是空转**。唯一真读项目 `.npmrc` 的是交叉校验的 `readRegistryFromNpmrc` —— 于是
  **校验的首选**与**实际安装的那家**可以不是同一家。本批的修法：`resolveRegistry` 成为唯一读数点，
  既喂交叉校验的 primary、也决定实际安装（`--registry` 不再无条件注入，改由 `--userconfig` +
  拷进 workDir 的项目 `.npmrc` 表达）。

**测试（本机与 CI 同源）**：

- `:domain:test` 139 例全绿（新增 `NpmRegistryKeysTest` 8 例：非 https/空/无 host/形态非法各自
  被拒且**原文点名**、带子路径/尾斜杠/端口/query 的 https **不被误拒**、`canonicalize` 去尾斜杠
  且子路径保留；`PackageManagerFacadeContractTest.门面方法面冻结` 的 `expected` 集合同步加两条）。
- `:app-service:npm:test` 231 例全绿（新增 `NpmGlobalConfigTest` 7 例，含"设镜像源不吃掉文件里
  别的键"；`HostNodeExecutorArgvTest` 5 例**零 node** —— 直接调 `npmArgv` 纯函数断言缺省 argv
  **不含** `--registry`、`registryOverride` 非 null 才含、`--userconfig` 与 `--registry` 可共存；
  `InstallCoordinatorTest` 新增 7 例，含"两层解析——项目 npmrc 有则用项目，没有才落到全局"、
  "校验不过抛原文且不落盘"、"快照带上全局镜像源读数"）。
- `:app:testDebugUnitTest` 与 `:ui:testDebugUnitTest` 全绿（`AppShellNpmCliTest` 新增"装配出的
  执行体：有 userconfig、没有钉死的 registry"—— 走**真 `AppShellKit.wireNpmExecutor` 生产路径**，
  这是唯一能钉住"断链 1 不再复发"的断言；`RegistryStateTest` 12 例，含"读失败保留已读到的值"、
  "读口未接线时是失败态而不是出厂值"、"空输入是恢复出厂而不是设为空串"、"写失败不清值也不回执"、
  "刷新不冲掉用户正在打的半截地址"）。

**未做（明确划界）**：首启引导的 registry ping 探测与镜像候选表（§10.9 第 6 条）、审计页
（`InstallHistory` 仍无 UI 消费方，本批只保证写进去）、`proxy`/`cache-retention` 两个 `NpmConfigKey`
（桥面本来就没有入口）、`NpmServices.registryOf`（该成员全仓零引用，本批不模仿也不顺手删）。
**真机面**：镜像源在真机网络下能否连通（企业内网/自建 registry 的证书与代理）、`--userconfig`
在 Android 上的路径可达性 —— 要装包才验得到，归入真机验证积压。

口径见 [`design-decisions.md`](../design-decisions.md) 第 53 项。

### 2026-10-09 —— 批 82：脚本全局环境变量（§8.1 新增契约）—— 管理面板「环境变量」落地

管理面板批 46 画了四项入口（「依赖管理 / 环境变量 / 日志管理 / 镜像源管理」），当时全是 toast
占位。依赖管理批 81 落地、日志管理早已落地，**「环境变量」与「镜像源管理」两行至今仍是
`toast?.show("…尚未开放")`**。

动手前先查契约面：**「环境变量」在 12 卷设计里没有对应条目** ——
`grep -rn "环境变量" docs/design/*.md` 只命中 §11 的 token 段与 §13 的 apksigner 口令段。
所以本批**不是接线既有契约，而是新增契约**：先写进 §8.1 再动代码。

**归属裁定**（用户口径原话「是给脚本的全局环境变量」）：管理面板的「环境变量」= 用户编一组 KV，
**所有脚本执行时注入脚本进程的 `process.env`**。不是宿主的、不是 npm 的、不是构建期的。

**四个提交**：

1. `feat(domain)`：契约 —— `com.autoscript.domain.scripts.ScriptEnvStore`（`all`/`put`/`remove`）+
   `ScriptEnvEntry` + `ScriptEnvKeys`（键名校验的**唯一一份**判据，`:ui` 与落盘实现共用，不抄两份）。
   `:domain` 零文件 IO，故契约住这里、jsonl 实现必须住 `:app-service:*`。
2. `feat(script-repo)`：落盘 —— `core/FileScriptEnvStore`，`files/.autojs/script-env.jsonl`，
   与 `tasks.jsonl`/`approve-ledger.jsonl` 同族纪律：追加 + `force(true)` 才返回、启动 replay
   全量重建、**容忍最后半行**（按字节扫 `\n` 而不是 `split` —— 值里可能有换行，split 会把一行
   撕成两行）、损坏行**响亮失败**（静默跳过 = 用户以为存了其实没存）、零第三方依赖（编解码走
   `:domain` 的 `DomainJson`）。
3. `feat(engine)`：注入面 —— `NodeEngineConfig.scriptEnv: () -> Map<String, String>`，
   在 `NodeProcessEngine.execute` 构造子进程 env 时调用。**顺序即契约**：用户键**先**写、
   宿主键（`AUTOSCRIPT_LIBNODE`/`AUTOSCRIPT_HOST_SOCKET`/`AUTOSCRIPT_BRIDGE_TOKEN`/
   `AUTOSCRIPT_RUN_ID` 等）**后**写，故宿主键一律胜出。
4. `feat(app,ui)`：装配 + 读口 + 界面 —— `AppShellApplication` 建 store、在 `engineFactory`
   闭包里捕获后传进 `NodeEngineConfig`（`AppShell`/`AppShellKit`/`AssembledShell` **零改动**：
   那三处 `assemble` 有 12/20 个测试调用点，加参数是纯噪声）；`HostSummary` 三条
   （`scriptEnv`/`putScriptEnv`/`removeScriptEnv`）；`:ui` `ScriptEnvState`（纯数据）+
   `ScriptEnvOps`（三个顶层挂起函数）+ `ScriptEnvScreen`（列表 + 删除 + 底部新增行）+
   `ManagementScreen` 那一行接上真入口。

**四条已拍口径**（全文见 [`design-decisions.md`](../design-decisions.md) 第 52 项）：

- **全局一份，不做按项目覆盖**（用户口径就是全局）；
- **每次 spawn 现读**（`() -> Map` 而不是装配期定死的 `Map`）：改完**下次执行即生效**，不必重启 App。
  装配期快照 = 用户在界面改完却不生效，正是本仓反复点名的坑；
- **不注入 npm 安装会话进程**：`HostNodeExecutor` spawn 的 npm CLI 是宿主工具进程、不是用户脚本，
  零 spawn 门禁（§11）的注入面越窄越好；
- **拒绝保存 `AUTOSCRIPT_` 前缀的键**，保存时当场报错并**点名那个键**。理由是实证：
  `AUTOSCRIPT_BRIDGE_TOKEN` 是宿主签发的一次性桥凭据（`main.cpp` 用它做 hello/ACK，认证后
  `unsetenv`；JS 侧 `bootstrap.ts` 认证成功后也 `delete process.env.AUTOSCRIPT_BRIDGE_TOKEN`），
  用户覆盖它 = 伪造桥身份或自断桥。spawn 时宿主键后写再兜一次底 —— 两道防线：写入侧拦住是
  「告诉用户」，spawn 侧兜住是「用户绕过界面改盘上文件也伤不到桥」。前缀判据**大小写敏感**：
  宿主键全大写，`autoscript_foo` 不撞任何宿主键，拦它属过度收窄（有单测钉这条）。

**呈现面不冒充**（四条，各有单测）：读失败**保留已读到的那份**并带原文（一次瞬时 IO 失败不该把
用户编好的表显示成空表）；键名不合法只进 `opError` 且**草稿留着**（清掉等于把用户打的字吞了）；
空串值是**合法值**且与「没设」在列表上是两条不同的事实（渲染成 `KEY=` 而不是留个洞）；
写失败**不清表**（宿主拒绝时先改表会出现「列表上没了但盘上还在」）。

**不持有常开 channel**（与 `FileTaskStore` 的差别）：这份表由用户点击驱动，写入频率以「次」计，
为它常开一个 `FileChannel` 换来的是「谁负责关」这个新问题（`AssembledShell.close` 关的是意图日志/
档案/任务注册表，本表不归壳）。改成每次追加现开现关 + `force(true)`：语义一样（返回前已落盘），
少一个生命周期。

**验收**：`./gradlew detekt`（全模块）绿 —— 新增 `@Composable` 与 `MainActivity` 越
`TooManyFunctions` 线各按既有做法落进 `ui/detekt-baseline.xml`（`detektBaseline` 与 `detekt`
分两次调用，重生成后 `--rerun-tasks` 复跑确认收敛）；CI 同源那条 14 任务 JVM 线全绿；
`lintDebug` + `:app:assembleDebug` 绿；文档链接门 559、冻结面门通过。

**一处如实降级**：计划里「`AppShellApplication` 侧读口至少一条『校验不过抛原文』」这条
**没做成** —— `AppShellApplication` 是 `Application` 子类，`filesDir` 要 Android `Context`，
而本仓**没有 Robolectric**（`grep -rn robolectric` 零命中），JVM 单测里构造不出来。
该判据的**实质**由两侧分担覆盖：写入侧 `FileScriptEnvStoreTest`「键名不合法抛原文且不落盘」
+ 呈现侧 `ScriptEnvStateTest`「键名不合法只进 `opError` 不落表」，而两侧调的是**同一个**
`ScriptEnvKeys.reject`（这正是它住 `:domain` 的理由）。`AppShellApplication` 那三段只是
`checkNotNull` + 转发，**没有本批新增的判据**。

**边界**：脚本进程 `process.env` 的实际可读性、以及用户设的值与 Node 自身 `process.env`
的交互，要装包才验得到 —— 归入真机验证积压。

### 2026-10-09 —— 批 81：依赖面板 + 审批卡（§10.9.1 / §10.9.2）—— 审批链从此有生产落点

§10.9 第 1/2 条（依赖面板、审批卡）在契约里是 P0，`design-status.md` 与 §11.3 第 6 条把它记成
「UI 未排期」。本批先做了一次实测复核，结论是**不是排期问题，是结构问题**：

- `PackageManagerFacade.resolveApproval` 与 `pendingApprovals` **全仓零生产调用方**（只有测试调），
  `ApprovalLedger()` 的 `store` 缺省 `null` —— 于是：审批票永远停在 PENDING、
  `runScript`/`exec` 永远过不了那道闸（T1 面等于纸面存在），重启后 `requestId` 还从 `apr-1` 重来、
  与历史票碰撞（`resolve` 按 requestId 查表，新旧账就此串在一起）；
- `NpmShellKit.assembleHandler` 建 `ApprovalLedger()` 时**没传 store** —— 已实现且已单测的
  `FileApprovalStore`（`files/.autojs/approve-ledger.jsonl`）**零生产调用方**；
- 管理面板的「依赖管理」是 toast 占位，而底下 14 个桥方法 + `storage()` + 审批入队口**都在**。

**三个提交**（每个一个逻辑完成点）：

1. `fix(npm)`：`NpmShellKit` 的 `approvalStore` 缺省改成 `FileApprovalStore(filesDir/.autojs)`
   —— 生产路径**不该**传 null，逃生口（`approvalStore = null`）保留但显式。两条新单测：
   缺省落盘（`requestApprove` 后 `approve-ledger.jsonl` 真在盘上、含 `"op":"submit"`）、
   显式不落盘（盘上零文件）。顺带订正 `ApprovalLedger`/`FileApprovalStore` 的 KDoc：
   真实文件名是 `.jsonl`，§10.2 正文里那处 `approve-ledger.json` 是过期写法。
2. `feat(domain,npm)`：读口 —— `PackageManagerFacade.snapshot(): NpmPanelSnapshot`
   （`projects` 按项目号排序 + `pendingApprovals` **全局**队列）+ `HostSummary.npmSnapshot()` /
   `resolveNpmApproval()` + `AppShellApplication` 两条实现 + `AssembledShell.npmFacade` 字段。
   读口**不经桥**（桥面是脚本侧的面，依赖面板是宿主自己的界面），桥面方法表**一条不加**。
3. `feat(ui,npm)`：`NpmScreen`（管理面板 → 依赖管理，两个分段：已装依赖 / 待审批）
   + `NpmState`（纯数据，JVM 可测）+ `MainActivity` 的 `reloadNpm`/`decideApprovalOp`。

**为什么读口是「全量一次现取」而不是「按项目问一次」**（本批中途改过一次口径，值得记）：
初版做成 `npmSnapshot(projectId)`、把 `pendingApprovals` 挂在项目上。随即发现两个问题 ——
① 审批队列在数据上**没有项目维度**（`resolveApproval` 不带 projectId、`ledger.all()` 是全局的），
按项目筛会让用户**漏掉别的项目上等着的那张卡**，那正是本批要修的缺陷本身；② 按项目问 N 次 =
N 次目录遍历 + N 套「读失败该怎么办」的分叉。改成全量后，项目列表取 `storage()` 的键
（项目根下的目录）而不是 lockfile 的键：装了依赖但还没落 lock 的项目也有一棵 `node_modules` 要管。

**命名**：`:domain` 的快照 DTO 叫 `NpmPanelSnapshot` 而**不是** `NpmSnapshot` ——
`app-service/npm` 里已有一个 `NpmSnapshot`（§10.9.4 高信任快照导出/验签的执行体），
两个同名类在 `InstallCoordinator` 里 import 撞车（编译期实测撞了）。名字先到先得，后者改名。

**呈现面刻意不做的三件事**（做了就是撒谎，理由写在 `NpmScreen` 的文件头 KDoc）：
不画安装输入行/进度条（读口只到"看"这一层，画一个按下去必失败的框比不画更糟）、
不画依赖树（`list(depth)` 宿主侧只用 0，画树就是把平铺清单伪装成树）、
不画 0% 配额条（尺寸没量到时显示「未量到」，0% 是在说"这个项目不占地方"）。

**顺带的结构整理**（不是洁癖，`onCreate` 已贴着 detekt 的 `LongMethod` 线 120）：
项目页与三个管理子屏抽成 `ProjectTab` / `ManagementSubPageHost`；三个子页开关收成一个
`ManagementPage?` —— 路由、返回键让位、切页现取**三处同序**（控制台 → 依赖 → 日志）；
`TabReloadEffect` 从"把开着的都读一遍"改成**按在前台的那一个**现取（依赖面板要遍历
`node_modules` 算尺寸，在别的子页上白跑是真金白银的 IO）。

**验收（本机）**：`:domain:test`、`:app-service:npm:test`、`:ui:testDebugUnitTest`、
`:app:testDebugUnitTest` 全绿（含新增 `NpmStateTest` 9 例）；`:domain`/`:app-service:npm`/`:ui`/`:app`
四模块 detekt 绿（`ui`/`app` 的 baseline 随新增的 `@Composable` 与 `AssembledShell` 构造参数同步重生成）。
**边界**：真机行为未验（无设备）；`NpmScreen` 的**安装**半边（输入行/进度条/依赖树）**未落**，
本次只落"看"与"批"两条。

### 2026-10-09 —— 批 80：`child_process` 拦截 shim 接线 + 零 spawn 金标准（§10.11 P0 / §10.12 末行）

§10.11 P0 与 §10.12 末行一直把「安装会话强制注入 child_process 拦截 shim」写成 P0 承诺，并给了
CI 金标准（child_process 替换为 throw 的 harness 里跑全命令矩阵必须全绿）。它此前**一直未落**：
`--ignore-scripts` 只挡 lifecycle 脚本（版本无关，见 §10.12），挡不住**非脚本** spawn —— npm 自己
新增一条 `execFile` 路径、或某个包在 `bin/` 里直接 `require('child_process')`。那类漂移在本平台上
的表现是**静默失败**（装完了但东西不对，无人报错）。本批把它变成可判定的不变量。

**新增三件（`:app-service:npm`）**：

- **`src/main/resources/com/autoscript/appservice/npm/npm-spawn-gate.cjs`** —— shim 本体。
  七个入口（`spawn`/`spawnSync`/`exec`/`execSync`/`execFile`/`execFileSync`/`fork`）全替换为抛错：
  非批准 spawn → `ERR_NPM_SPAWN_BLOCKED`；`detached:true` → `ERR_PERMISSION_DENIED`
  （§10.3 T1 明写「shim 直接拒绝 detached/setsid」：脱离进程组的子进程回收不到）；`fork` →
  `ERR_NOT_IMPLEMENTED`（§10.3「明确不可行」）。错误**必须带 `.code`**（Node 的错误折叠面认它，
  普通 Error 会被折成 `ERR_INVALID_PARAM` = 把「被门禁拦了」说成「参数错了」），并往 stderr 打一条
  `[npm-spawn-gate] <CODE>: <detail>` 播报（`redirectErrorStream` 后是唯一能到宿主的通道）。
- **`NpmSpawnGate`** —— 落位 + 注入串 + 播报解析。shim 住 classpath 资源、落到
  `filesDir/.autojs/`（**不随 npm 素材树**：素材树受 `npm-manifest.json` 逐件摘要对账，
  塞宿主自己的文件会让「清单与 APK 文件集合不一致」每次启动必红）；`mergeNodeOptions` 把
  `--require=<落点>` **追加**进已有的 `NODE_OPTIONS`（不覆盖父环境里那份别人的设置）；
  `blockedIn` 从合并输出里取**最后一条**播报（npm 重试时杀死会话的那次才是病因）；
  `errorCodeOf` 把播报码折成领域错误码，认不出的折回 `ERR_NPM_SPAWN_BLOCKED`。
- **`HostNodeExecutor` 新增 `spawnGateFile`**：非 null 时注入 `NODE_OPTIONS`，非零退出时
  **门禁播报优先于「退出码 N」**（被拦时 npm 只笼统报一句失败，真病因是 shim 那条）。

**装配层 fail closed**：`AppShellKit.wireNpmExecutor`（自 `assemble` 外迁的 60 行，装配根已经三十几个
参数）把「素材落位 + 有 Node 宿主 + shim 落位」三条串起来 —— **任一不成立就保持
`HeavyOpExecutor.Unavailable`**。shim 落位失败**不注入执行体**：它是 P0 承诺面，静默降级成
「装是能装、守卫没了」正是那条风险本身。原因原文进 `npmCliFailure`，不吞。缺省资源永远在
classpath 上，故这条分支由新增的 `npmGateDeploy` 注入缝在测试里够到；`AssembledShell` 新增
`npmSpawnGate` 字段（非 null = 守卫在盘上）。

**零 spawn 金标准落成 `NpmSpawnGateMatrixTest`**（§10.12 末行那条要求的落地）：① 门禁注入下
install/ls/dedupe/prune/uninstall/ci 全绿且零播报；② 同一条矩阵**不注入也全绿**（反向变异：
少了它「全绿」可能只是矩阵本来就没跑起来）；③ `npm run <script>` 在门禁下确实被拦 ——
判据是**产物文件在不在**（脚本正文会回显在 npm 输出里，拿词表判会自己骗自己），并先证明无门禁时
该脚本真跑过。只用本地 `file:` 依赖（零网络），故能进 PR 门；已登记进
[`check-e2e-ran.sh`](../../.github/scripts/check-e2e-ran.sh) 的 nightly 验尸清单
（本机没 npm 时跳过是对的，CI 上恒真跑）。

**验证**：本机 14 任务 JVM 线全绿；`NpmSpawnGateTest` 9 例（含两例**真起 node** 验七个入口 +
一例反向证明拦住它的是 shim 不是环境 + 两例执行体注入）与 `NpmSpawnGateMatrixTest` 3 例全过；
去掉 `-PskipNpmE2E` 跑 `check-e2e-ran.sh` **四条真 npm 路径全部 ✓**；`lintDebug` + `assembleDebug` 绿，
`npm-spawn-gate.cjs` 实测进了 APK（`unzip -l` 可见，4799 字节）。

**边界（写死，别当它是沙箱）**：本 shim 是**不变量守卫**，不是安全边界 —— 已获批的脚本可以
`delete require.cache[require.resolve('child_process')]` 后重新 require 拿到未打补丁的模块。
真正的对抗面是审批（§10.5-2 人机分离）与 T1 会话的最小 CapabilityMask（§10.5-4）。
口径见 [`design-decisions.md`](../design-decisions.md) 第 50 项。

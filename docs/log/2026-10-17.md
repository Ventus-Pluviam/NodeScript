### 2026-10-17 —— 设备实测：装依赖抛 `NetworkOnMainThreadException`（交叉校验取 packument 落在主线程上）

**用户报（原文）**：「安装依赖报错，networkonmainthreadexception」。报源是上一版真机包
（`42355cc5`）的用户自测。

**病**：`InstallCoordinator.crossCheckRegistry`（§10.5-1 多镜像交叉校验）调
`NpmRegistryVerifier.verify`，后者走 `HttpRegistrySource.packument` —— **同步阻塞**的
`HttpURLConnection`（每个包两趟 packument，`connectTimeout` 5s + `readTimeout` 8s，不跟随重定向）。
整条链确实是 suspend 的（`submitInstall` → `HostSummary.runNpmPanelCommand` →
`AppShellApplication` → `InstallCoordinator.runConsoleCommand` → `install` → `crossCheckRegistry`），
**但 suspend 只给「可挂起」的许可，不搬线程** —— 界面那条协程是 `MainActivity` 的
`rememberCoroutineScope()`（= Main），于是取 packument 就落在主线程上，Android 当场抛，
**一个包都还没发出去**（`crossCheckRegistry` 摆在 `enqueueHeavy` **之前**，那是"先校验再排队"
的刻意次序）。

为什么本机与 CI 都抓不到：本机 JVM 根本没有那道守门人（`NetworkOnMainThreadException` 是
Android runtime 的），而单测里原本没有任何"谁在哪个线程上跑"的断言 —— **这一类只能由设备实测发现**。

**药**：`verify` 包进 `withContext(Dispatchers.IO)`。这是**本文件既有的写法** ——
`cacheStorage()` 早就是 `withContext(Dispatchers.IO) { … }`，`HostNodeExecutor`/`NpmScriptExecutor`
同理，这条只是先前漏了。落点选在 `:app-service:npm` 而不是「在 `:ui` 把宿主调用整体包一层」：
**做阻塞调用的那一层自己声明它是 IO**，且该模块是纯 JVM（`Dispatchers.IO` 是协程概念、不是 Android
依赖），archUnit 不受影响。另**全仓 main 源码扫过**：`HttpRegistrySource` 是**唯一**的网络调用点
（`java.net` 的其余命中全是 `LocalSocket`/`SocketChannel` 的本地抽象套接字与 `URLEncoder`），
故一处即够。

**回归闸**（本机 JVM 里那道守门人的替身）：新用例 `取 packument 不落在调用线程上` ——
假校验缝里记 `Thread.currentThread()`，断言它 ≠ 调用方线程。依据是「界面与控制台都是拿自己那条
协程**直接 await 整条 install 链**的」，所以"verify 跑在调用方线程上"就等价于"落在主线程上"。
**已对拍（这一步不能省，否则是条不会红的假闸）**：把那一行 `withContext` 去掉后该用例红，
原文 `expected: not same but was: <Thread[main,5,main]>`；加回来 99 例全绿。

**验**：`:app-service:npm` main + test 全量本机编译零 error；JUnit launcher 真跑该模块 25 个测试类
（除 `ArchitectureTest` —— 它要 `build-logic` 的 ArchGate，本机不装）—— `InstallCoordinatorTest`
99 例全过；`NpmSpawnGateTest`/`NpmSpawnGateMatrixTest`/`T1BridgeE2ETest`/`T1BridgeNodeTest`
四个类本机红（缺装配期生成的 shim/asset 树与 `noden` 二进制），**已拿 `HEAD` 版同一份源码对拍，
红数逐字相同**（4/2/6/6）⇒ 与本改动无关；detekt `:app-service:npm` main + test 零 findings
（baseline 未动）。

**顺带说清一件事（不是 bug，是设计）**：交叉校验排在 `enqueueHeavy` 之前，而它要联网取两份
packument —— 所以**按了安装之后到 npm 真开始之前，最长可以等 (5s+8s)×2×包数**。这条次序是有意的
（"若放在门禁之后，磁盘不够也会先付这次的网络代价；先校验再排队让用户在等锁时拿到的就是最终结论"），
但用户看到的是"按了没反应"，届时按这个口径解释。

同批推翻/订正：无。

### 2026-10-17 —— CI 红修：`onAbsolutePath` 的返回类型写成了 `Unit`（本机"过滤掉了真错误"）

**红**：`:ui:compileDebugKotlin` ——

```
ProjectScreen.kt:576:54 Argument type mismatch: actual type is 'kotlin.Unit', but 'kotlin.String' was expected.
```

JVM 单测与 Android 构建与 Lint 两个 job 同一条红（engine-native 也随之失败）。这一次**没有测试红**：
`:domain`/`:app`/`:ui` 的 92 例本机跑过的全绿，红的是**编译**。

**病**：`HostSummary.absolutePathOf` 的呈现层接缝 `onAbsolutePath` 我写成了
`suspend (String, String) -> Unit` —— `onDelete` 是 `Unit`，抄顺手了。唯一会红的调用点是
`copy.copy("已复制绝对路径", onAbsolutePath(...))`（要的是被复制的**那条路径**）；
`MainActivity` 那边传的 lambda 返回 `String`，而 **Kotlin 允许把有返回值的 lambda 往 `Unit`
上强转**，所以只有真正取值的那一处炸。

**药**：参数类型改回 `-> String`；`ui/detekt-baseline.xml` 里那两条 `ProjectScreen` 的签名文本
（`FunctionNaming` / `CyclomaticComplexMethod` —— detekt 按签名**原文**匹配）跟着重生成，
它们本来就含被改的那个类型。

**本机为什么没抓到（这一批最值钱的一课）**：本机没有 Android SDK/Compose，`ProjectScreen`/
`MainActivity` 编不了，只能"带 `:ui` 已编好的 state 类空编一遍、看有没有真错误"。上一轮我用的过滤是
`grep -E "expecting|unresolved reference: <新符号>"` —— **过窄**：`Argument type mismatch` 这类
**两边类型都解析得到**的错误一条都没进过滤表，**编译器其实报了，我没看**。这次改成**白名单式**
过滤（只滤 cascading 的 `unresolved reference` / `cannot infer type` / `ERROR CLASS` 一类），
同一条错误立刻浮出来；并与**改动前的同一份文件**对拍，确认剩下的 3 条全是本机假象
（2 条改动前就有、1 条是 `internal` 的跨编译模块可见性）。

**教训**：`unresolved` 过滤是"本机没有依赖时的必要之恶"，但它会**连真错误一起滤掉** ——
判据应该是"**哪些错误是依赖缺失导致的**"（白名单），不是"**我想看哪些错误**"（黑名单）。
同一条纪律此前在文档链接门那边踩过（"本机绿 ≠ 门禁有效"），这次是它在家门口的复现。

### 2026-10-17 —— 文件列表菜单改三项（复制相对/绝对路径 + 删除）+ 多选批量删除（用户口径）

**用户口径（原文）**：「文件列表的菜单栏，取消进入文件夹这个选项。复制路径改成复制相对路径，
复制绝对路径2个，再加个删除」。两个追问当场裁定：① 菜单的「删除」落在**根层的文件夹**（= 一个项目，
`files/scripts/<名字>/` 整个目录）上 → 「**允许，不用加弹窗**」；② 多选模式要不要批量删 →
「**顺带做上**」。

**宿主侧补两个口**（此前一个删除口都没有，呈现层也拿不到绝对路径 —— 它不知道 `filesDir`）：
`HostSummary.deleteEntry(projectId, relPath)`（**文件夹递归整棵**；不存在**抛**，静默成功会把
"删错了对象"与"删掉了"画成同一件事）+ `HostSummary.absolutePathOf(projectId, relPath)`
（**不查存在性** —— 与 `ScriptPaths.scriptFile` 同一条分工"约定只回答应该在哪"，刚删掉的行照样
复制得出它原来在哪）。两个都写成**抽象成员**而不是 `runScriptFile` 那种缺省抛：全仓只有两个实现者
（`AppShellApplication`、`:ui` 的 `FakeHost`），抽象能把"没接线"变成**编译期红**。

`:app` 侧落点全在 `ScriptFileOps`，与既有四口共用同一条 `resolveInProject`（防越界 + 首段与项目名
一致 + 根层单段）：`delete` 多两道闸（目标必须存在；不许是 `files/scripts/` 本身 —— 根层单段判据
理论上已挡，但那条闸挡的是"删掉整个项目库"，值得自己有句话），删目录走 `walk` 逆序 + `deleteIfExists`
（`Files.delete` 对非空目录抛 `DirectoryNotEmptyException`，而"删文件夹"在用户眼里是一个动作）；
`absolutePath` 就是 `resolveInProject(...).toString()`，**不另写一套容错拼法**（拼错的方向是"复制出去的
路径指向另一个文件"，而用户拿它去别处用时不会再有人校验一遍）。`AppShellApplication` 两个 override
与 `createEntry` 同一句口径：只看 `files/scripts/` 落盘、**不依赖壳寄存器**（装配中/失败时删除照常可用）。

**呈现层**：菜单三项 —— 「复制相对路径」（= 原「复制路径」改名，值不动）/「复制绝对路径」
（宿主现取，**失败原文说出来**，不静默复制一条空的）/「删除」（`StatusTone.PROBLEM` 红字，
**点了即删、不弹确认框**）。「进入文件夹」那一项**删掉**了：点目录行本身就是进一层，菜单项与主手势
重复了一件事。选择模式顶栏加一格「删除」（排在「选择全部」**右侧**：破坏性动作不放拇指先够到的位置），
点完**退出选择模式**（行没了，选中集里不能留幽灵键 —— 留着的话顶栏还写"已选 N 项"）。批量目标由新增的
纯函数 `deleteTargets(selected, files)` 算：**剪掉被另一个选中项包含的后代** + **深度降序** ——
搜索态的池子是**整棵树**，父子可以同选，先删父再删子会让子项那一下撞"条目不存在"**假报失败**；
前缀判据靠目录行 relPath 的**尾随 `/`**（`"demo/lib/"` 是 `"demo/lib/a.js"` 的前缀，`"demo/lib"` 不是，
少了这个斜杠 `lib` 会误吃掉 `liba.js`）。它住在**文件顶层而不是 `ProjectState.Companion`**：那是操作语义
（选中 → 要删哪些）而不是同伴对象里"选中集 ↔ 可见集"的读取语义，且那个 companion 已贴到 detekt
`TooManyFunctions` 上限（11）—— 同批 `ScriptFileOps` 也因此在 11 个函数上把 `requireName` 与
`requireProjectName` **合成一个**（判的是同一个东西：这个名字，只是"落盘后是不是项目目录"多一档）。

**代价与已知边界（如实记）**：① **删除不弹确认框**（用户口径）—— 不可撤销、**没有回收站**，
菜单项是红的但误触即永久丢失；② **根层文件夹可删 = 可以一次删掉一整个项目**（用户裁定"允许"）；
③ 删除**不检查在途执行**：引擎已把脚本读进内存，删文件不打断本次执行，下一次投递才是
`ERR_FILE_NOT_FOUND`；④ 编辑器里正开着被删的文件时，「保存」得到的是既有的诚实拒绝
「文件不存在（不新建）」，不另加逻辑。

**本机验了什么 / 没验什么（禁本地 gradle）**：① 编译 —— `:domain` 全量零 error；`ScriptFileOps`/
`ScriptFilesRead`/`DeployPath` 与 `:ui` 四件纯状态文件、两个测试文件分别编过；`ProjectScreen` 带上
`:ui` state 类编过（`deleteTargets` 引用解析得到）。② **真跑（JUnit launcher）92 例全绿**：`:domain` 44
（`TypedIdsTest` 11 / `ScriptPathsScriptFileTest` 8 / `ScriptPathsProjectInternalTest` 4 /
`NpmConsoleKeysTest` 21）、`:app` 32（`ScriptFileOpsTest` **27** 含新增 6、`ScriptFilesReadTest` 5）、
`:ui` 16（`ProjectStateTest` **16** 含新增 2）。③ detekt（仓级 yml + 各模块 baseline）
`:domain`/`:app`/`:ui` 零 findings —— 为压住 `TooManyFunctions` 做了上面那次合并，`:ui` baseline
**外科式改 2 行**（`ProjectScreen` 签名多了两个参数 ⇒ 它的 `FunctionNaming` 与
`CyclomaticComplexMethod` 两条 baseline 的签名文本跟着变；这两条是 detekt 按**签名原文**匹配的）。
④ 文档链接门。**没验**：Compose 面本机编不了（本机没有 Android SDK），菜单观感与真机删除路径
归设备侧自测。

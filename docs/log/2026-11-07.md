**一、§7.4「GC 兜底」从未存在（契约订正，决策第 106 项）**。审计 #148 时三条事实叠加成漏洞：
① §7.4 写「显式 `dispose()` + `FinalizationRegistry` 兜底；GC 时向内核发 `release(id, gen)`」、
「引用计数对象用弱引用 + finalize 兜底」，§9.2 写「`recycle()` 显式 + finalize 兜底」——
但全仓（`.ts`/`.js`/`.cjs`/`.mjs`/`.cpp`/`.cc`/`.h`/`.kt`）grep **零 `FinalizationRegistry`、
零 `WeakRef`、零 `napi_add_finalizer`**；唯一的 env 清理钩子是 `bridge_addon.cc:371` 的
`napi_add_env_cleanup_hook(env, TsfCleanup, …)`，那是**进程退出时**拆桥 TSF 的，不回收任何帧。
② native 帧表（`imgnative.cpp` 的 `g_frames`）**没有批量释放口**，只有单条 `imgnative_release`。
③ `NativeImageAnalyzer` 是 `SystemSpis.of` 装配期建的**进程级单例**，帧账活过 run/连接终结。
量级：1080×2400 RGBA ≈ 10.4 MB/帧、333ms 节流 ≈ 31 MB/s，只进不出。

**修法（#148 已合入）**：兜底不建在 GC 上，建在**连接生命周期**上 —— 与投屏会话
（批 75，决策第 48 项）同一条 `ConnectionResourceRegistry` 路：帧账记「发它的那条连接」
（`AuthenticatedRunContext.connectionId`），首帧时为该连接登记**一条**回收闭包
（一连接一条，不是一帧一条；并发重复登记者的败方句柄立即 release），连接终结
（abort/dispose/自然退出）即回调 `NativeImageAnalyzer.releaseConnection(connectionId)`，
把该连接名下在场帧全部还 native。按 `connectionId` 分区互不误收；无认证身份的调用
（宿主直调/JVM 测试）落 `NO_CONNECTION` 分区、不登记（没有连接可撤销，登记了就是假装有兜底）。
**为什么不补 `FinalizationRegistry`**：GC 时机不可控、不可测，而兜底语义要的是
「脚本死了帧一定还」—— 连接终结恰好是这个事实的可靠信号，且注册表已存在（投屏在用），
边际成本最低；将来若真补 GC 网，是在其之上再加一层提前量，不替代连接级收口。
守卫：`NativeImageAnalyzerConnectionReclaimTest` 17 例（首帧登记一次/多帧一闭包/分区互收/
无身份不登记/重复登记败方释放/native 失败经 `onError` 上报不中断余帧等）。

**二、「发过的号」账换号段水位（#149 已合入）**。`AndroidSensorSource.closedEver` 与
`AndroidFloatingWindowHost.everIssued` 都是进程级单例上的**只进不退** `HashSet<Long>` ——
按调用次数无界增长，而它们要回答的只是「这个号发没发过」一个**区间**问题。
改为 `lastIssued` 高水位 + `issuedLocked(refId) = refId in FIRST_REF_ID..lastIssued`
（O(1)、精确；仓里 `ABANDONED_KEEP`/`FINISHED_KEEP`/`RECORDINGS_KEEP` 三处留 64 条的裁剪法
在这里不够用 —— 裁过的集合会把「很久以前关的」误报成「没见过」，那正是要分辨的事实）。
**配套前提**：发号挪到 `ops.start`/`ops.add` **成功之后**、与入表同一把锁内 ——
否则被系统拒掉的那次消耗的号会落在水位以下、却从没进过 live，一个从没发出去的号
被报成「已关闭」。三个变异体全被守卫逮住（发号挪回成功前 / 水位不前进 / 区间下界丢掉）。

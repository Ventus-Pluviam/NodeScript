### 2026-10-08 —— 批 79：`lockKey` 生产接线（T2 lockfile 投毒防线由「代码在、装配没接」转为生效）

`LockSigner`（HMAC-SHA256 带外签名，`files/.autojs/lock.sig`）与它的单测从 2026-10-01 起就在，
但 `NpmShellKit.assembleHandler` 的 `lockKey` 一直走缺省 `null` —— **生产路径上 lock 既不签也不验**，
`npm ci` 对一份被换过的 lock 直接放行。§11.3 第 8 条自己记着这件事。本批接线。

**新增 `app/src/main/kotlin/com/autoscript/shell/LockKeyStore.kt`**（`:app` 装配层，Keystore 版按
2026-10-01 的落点拍板住这里）：

- **`HmacKeys` 是唯一碰 `android.` 的面**（`load`/`create`），`resolve` 与它的单测都是纯 JVM
  （`:app` 无 Robolectric，`AndroidScreenGate` 那套「缝 + 假件」同款分法）。
- **get-or-create 且「取不动」绝不静默重建**：只有 `load` 返回 null（别名下真没有这把钥匙）才 `create`。
  锁被换过/库失效（`KeyPermanentlyInvalidatedException`）、Keystore 整体不可用（锁屏态、厂商 ROM）
  一律**显式失败**。理由写进 KDoc：重建会把「这份 lock 曾被换过」洗掉，或者让所有项目已有签名
  一起变成验不过 —— 用户只看到一堆无法解释的 `ERR_PERMISSION_DENIED`。
- **别名带版本号** `autoscript.lock.hmac.v1`：落盘格式已是 `v1 <hex>`（那是将来换 ECDSA 的兼容开关），
  换算法时**换一把新密钥**而不是让旧密钥去签新格式 —— 否则「v1 签名验不过」与「算法换代」在诊断上分不开。
- 生成参数：`PURPOSE_SIGN or PURPOSE_VERIFY`（HMAC 密钥在 Keystore 里没有加密语义，`ENCRYPT_MODE`
  对它是错的）+ `BLOCK_MODE_GCM`/`ENCRYPTION_PADDING_NONE`（Keystore 通用模板要求，HMAC 不用但
  部分 ROM 不写全就抛）+ **`setUserAuthenticationRequired(false)` 写在明面上**（这道签名要能在
  息屏守时安装里跑；真正的门是「lock 必须由本机签过」，不是签的时候有没有人解锁）。

**接线三处**：`AppShellKit.assemble` 新增 `npmLockKeys: LockKeyStore.HmacKeys? = null` 缝 →
装配期**就取一次钥匙**（`resolve(keys).also { it.secretKey() }`）—— 不把「Keystore 坏没坏」推到用户
第一次 `npm ci` 才炸，那时看到的是一条验签失败，分不清是 lock 被换了还是钥匙取不动；
取不到**不外抛**（npm 只是能力之一，为一把钥匙掀翻装配不成比例），本次传 `null` = 不装该防线，
原因原文进**新增的** `AssembledShell.npmLockKeyFailure`（与 `npmCliFailure` 同一条「不吞」纪律，
但两处措辞不混：那条是「CLI 落了但跑不起来」，这条是「装得上、能装，只是 `ci` 不验签」）。
`AppShellApplication` 递 `LockKeyStore.AndroidKeystore`。

**验证（本机，与 CI 同源命令）**：新增 `LockKeyStoreTest`（4 例）+ `AppShellNpmCliTest` 加 5 例
（T2 接线面）；14 任务 JVM 线全绿、`:app` detekt 绿。**反向验证做了两次**：
① 把 `AppShellKit` 的 `lockKey = lockKey` 改回 `null` → 「无签名 lock 被 ci 拒」与「跨项目搬锁被拒」
两条当场红（**这就是本批的核心判据** —— 接线前 `ci` 对无签名 lock 是直接放行的，所以
`ERR_PERMISSION_DENIED` 只可能来自接上了）；② 把 `resolve` 的 get-or-create 改成「已有也重建」→
「库里已有：绝不新建」与「验签拒绝」两条红。两处变异各自命中它该命中的用例，随后还原。

**边界（如实记）**：真机行为未验（无设备，按用户规矩不连 adb）—— `AndroidKeyStore` 那一层
（`KeyGenParameterSpec` 参数在真 ROM 上收不收、`getEntry` 返回类型）只有装包才验得到；
本批验的是**判定**（get-or-create、取不动不重建、失败不掀翻装配）与**接线**（ci 真走验签）。
`detekt-baseline.xml` 因 `assemble` 多一个参数而重生成（只动了 `AppShellKit` 那条签名，
`AssembledShell` 构造超 12 参新增一条）。

### 2026-10-08 —— 批 77 补记：CI 首轮红在 `:app:testDebugUnitTest`（录屏接线用例写死设备路径）

批 77 推送后 CI 首轮 **JVM 单测门红**（其余六门全绿）：

```
PlatformWiringTest > 存储通知剪贴板传感图像七条独立缝经真 handler 落到假 SPI() FAILED
  Err(errorCode=ERR_IO, detail=... 录屏落点目录建不出来：/data/app/files/scripts/demo/.recordings（/data）)
```

**根因**：录屏腿的接线用例把 `filesDir` 写死成真设备路径 `Path.of("/data/app/files")`，
而 `MediaProjectionRecorder.specFor` 会 `Files.createDirectories` **真的去建目录** ——
CI runner 非 root 建不动 `/data` → `ERR_IO`；**本机 root 跑得动，于是在宿主根上真建出了 `/data`**。
两种结果都不是该用例要测的东西（它测**接线**：装配层把 `projection as? ScreenRecordingSessions`
接成 `MediaProjectionRecorder`、落点按 `ScriptPaths` 算），落点根只要是可写临时目录即可。

**这是「本机绿 ≠ 门禁有效」的又一例**：本机 14 任务 JVM 线当时报 1638/0/0/0，
而同一棵树在 CI 上红 —— 差别只在跑测试的用户权限。

**修法**（`4bebf4c`）：改 `@TempDir lateinit var dir: Path`，期望值用
`ScriptPaths.recordingsDir(dir, "demo")` **现算**，不写死绝对路径；宿主上误建的 `/data` 已清掉。
同批核过 `:app`/`platform` 其余测试的 `filesDir` 实参（都来自 `@TempDir`），无同类问题。

**修后**：`:app:testDebugUnitTest`（PlatformWiringTest）6/0/0/0；14 任务 JVM 线 1638/0/0/0；
CI 重跑**七门全绿**（JVM 单测 4m52s、Android 构建与 Lint、bridge/js、冻结面、文档链接、真形态 APK ×2）。

**轨一 · §8.5 意图日志落 SQLite（`5f8c6ca`，22 文件 +1857 −57）**

契约 §8.5 一直写的是「append-only（**SQLite**，启动即回放）」，而全平台生产跑的是
`JournalFileStore`（jsonl）。卡点是**接口住 `:app-service:scheduler`**（纯 JVM、零
`import android.`），依赖铁律 `:platform:*` → `:domain` 不反向 —— 要么搬接口，要么给
scheduler 加 Android 依赖（丢掉纯 JVM 可测）。**本批选了搬接口**：

- `IntentStore` 自 `:app-service:scheduler` **迁到 `:domain`**（`domain/scripts/`，`R055` 改名，
  签名/`StartRow`/`StoredRow`/`StoredOutcome`/`crashed(message)` 逐字未动，只重写 KDoc）。
  调度侧 `toIntentRun()`/`toStored()` 留在 `IntentStoreMapping.kt`（它依赖 scheduler 的
  `IntentRun`/`RunOutcome`，跟着搬会把 scheduler 的语义拖进 `:domain`）。
- 实现落 `:platform:system/persist/`：`IntentStoreSql`（纯 SQL 生成，可 JVM 单测）、
  `SqliteIntentStore`（语义）、`AndroidSqliteRunner`（**唯一碰 `android.` 的文件**）、
  `IntentStoreWiring`（选型 + 一次性迁移）。
- **两份实现跑同一套契约测试**：`:domain` 新增 `testFixtures` 源集放 `IntentStoreContract`
  （抽象类，16 例，子类只提供 `open(): IntentStore`），`JournalFileStoreContractTest`（16）
  与 `SqliteIntentStoreContractTest`（20）各自继承。**这条是本批最值钱的一步** —— 下面那条
  索引缺陷就是它抓到的。
- **幂等锚点 = 一个部分唯一索引，不是两个**：
  `CREATE UNIQUE INDEX ux_nonce ON intent_log(run_nonce) WHERE outcome IS NULL OR outcome <> 'INTERRUPTED'`。
  先写的两索引版（`WHERE outcome IS NULL` + `WHERE outcome IS NOT NULL AND outcome <> 'INTERRUPTED'`）
  **覆盖不重叠**，「同 nonce 已 COMMIT 之后再直投一条 START」两条都不拦 ——
  共享契约套件里 `同 nonce 已 COMMIT 拒绝直投` 先红，才逼出单索引写法。
- **runId 不复用**：`run_id INTEGER PRIMARY KEY AUTOINCREMENT`（`sqlite_sequence` 上抬，
  崩溃后不回收号）。理由不是洁癖 —— `runId` 与 `run-archive.jsonl` 的
  `EngineRunLink.intentRunId` **是同一批号**，复用会让新意向与历史 link 同号异义。
- **迁移是一次性、带原 runId、可重入**：库非空即跳过；全量导入包在一个事务里；
  **导完且验完才**把 jsonl 改名 `intent-log.jsonl.migrated`（不删）—— 导入抛错时老日志
  原样在原处，不会「导了一半、老的又没了」。存活行（未 COMMIT）导入后下次启动判为崩溃
  遗留并重投，**与 jsonl 路径今天的行为一致**（启动即回放）。
- **打开失败如实回落 jsonl**，原因经 `AppShellKit.IntentStoreChoice.fallbackReason` 随装配
  日志输出 —— 与 `images`/`dialogs` 同一条「缺件不伪造」纪律，回落是明说的降级。

  动它会碰到 §8.5 的幂等锚点（老终态行/老 nonce 能否丢），**本批不碰**，入池见 backlog。
- **反向验证做了两次**（不是只跑绿）：改坏索引 → 1 failed / exit 1；
  删掉 `JournalFileStore.insertStart` 的已 COMMIT nonce 守卫 → 1 failed / exit 1。
- **模块数仍是 17**：本批**没有新增 Gradle 模块**（那会动冻结面 `settings.gradle.kts` 与
  文档里的派生数字）。`domain/build.gradle.kts` 只加了 `java-test-fixtures` 插件。

### 2026-10-08 —— 批 75：执行级能力掩码与跨脚本授权（A5 第一阶段）+ MediaProjection 高清会话（§9.2）

两条轨并行开发、各自一个工作树，由协调者会话在集成树上合流（两个 merge 提交，无 squash）。

**A5 第一阶段 —— 把「脚本能碰哪些桥面」从无判据变成 deny-by-default 的执行级掩码**

- **判据与目录**（`:domain`，零 Android / 零桥）：`CapabilityMask` 是 `@JvmInline Long` 位集，
  位序取 `BridgeCapability.ordinal`，未申报位拒绝；`BridgeCapabilityCatalog` 给「命名空间 → 所需掩码」，
  方法级**整体覆盖**命名空间级（不是并集 —— 并集会让最轻的 `poolStats` 也被要求控制权，分档就白分了）；
  **未申报命名空间 = `CapabilityMask.ALL` → 一律拒**。
  `engines.stop` / `engines.status` 的**目录级**要求降到 `NONE`：路由器只看得见调用方掩码、看不见
  `runId`（那是 payload），目录一旦写跨脚本位，窄掩码脚本连**自己**都停不掉 ——
  「是不是别的执行」这条判据下沉到 handler。
- **来源档**：`TrustTier` 四档按 §11 冻结矩阵逐字取（内置/自写/第三方/打包 = 全量，**这不是安全声明**），
  矩阵之外新增 `UNKNOWN` 档取**保守档 A**（全量减 `CROSS_SCRIPT_CONTROL`/`CROSS_SCRIPT_OBSERVE`/
  `SCHEDULER_WRITE`，用户 2026-10-08 裁定，见 `design-decisions.md` 第 43 项）。
  `PACKAGED` 档同样落保守档（无验证配置时不自动升全量）。来源**只来自宿主持有的元数据**，
  绝不从桥 payload / projectId / 项目名推断 —— 那是脚本自报，不是证据。
- **单一决策链（杀 TOCTOU）**：授权快照在 `RuntimeController.start` 的同一把锁下**算一次**，
  随后 池请求 → `EngineRunRequest` → `RunIdentityIssuer.issue` → lease →
  `AuthenticatedRunContext.capabilityMask` 搬的都是**同一份对象**，下游不重算；
  `RunIdentityRegistry` 不再自己算授权（原先「预检算一套、签发算另一套」的窗口就此关闭）。
- **桥路由先授权后路由**：未覆盖 → `ERR_PERMISSION_DENIED`，且**不进请求账、不触达 handler**
  （未知命名空间也在授权之后才判「未实现」，不留探测面）。授权字段不上 wire、不从 payload 解码 ——
  与身份三字段同一条「不可自报」纪律。
- **跨脚本目标授权**（`CrossScriptAuthorizer`，纯函数）：自我操作放行；触达他人执行要
  `CROSS_SCRIPT_OBSERVE` / `CROSS_SCRIPT_CONTROL`，**且**调用方掩码必须覆盖目标掩码
  （否则低信任调用方只要有控制位就能停掉高信任执行）；目标授权查不到 → fail closed。
  「目标在不在途」由 `RuntimeController.authorizeTarget` 在同锁下判并回 `ERR_NOT_FOUND`
  —— 纯函数不拿整张在途表，不造第二份事实。
- **派生不得提权**：`engines.exec` 要求子掩码不超出父掩码（否则 exec 就是一条提权通道）；
  宿主发起的 run 是链的根，不受此限。
- **命名通道改为按发起执行私有**（名字索引按 owner 分桶，`HOST_OWNER = -1` 给宿主直投）：
  不同执行同名通道各拿各的 id，猜别人的 id → `ERR_NOT_FOUND`。改之前通道是一条绕过掩码的跨执行数据面。
- **`workManager.create` 注入 `authorizeCreate` 接缝**：**缺注入 = 全拒**（fail closed），
  且拒的时候不落盘；接缝回 `null` = 明确放行。「接缝在、回 null（放行）」与「接缝不在（拒）」
  是两种不同的「没有授权」，实现里分开表达 —— 原先的 `?: "缺判据"` 把两者混成一种，
  是六个调度测试同时红的真因。
- **行为变化（如实记账）**：无来源元数据时，跨脚本面（`engines.exec/stop/status/poolStats`）与
  `workManager.*` 对脚本拒；a11y / 截图 / 文件 / npm / 设备面保持全量。脚本默认**不能再自建定时任务**
  —— 已知功能回退，待来源元数据接入后由分级恢复。
- **设备侧三态门禁零改动**：掩码只决定「这次执行被授权用哪些桥面」，系统层给不给仍由
  `PermissionFacade` 现问系统；两张目录（设备 `Capability` vs 桥面 `BridgeCapability`）是两个枚举，不合并。
- **边界**：这不是沙箱（§11.3 第 1 条）—— 只约束桥面命名空间，不拦 Node 内建 `fs`/`http`，
  同 UID 代码仍可绕开桥直连进程与文件。本批掩码只驻内存，不落盘。

**MediaProjection 高清会话（§9.2 的另一条腿）**

- **会话生命周期**：进程级单会话账（`opening` / `openingOwner` / `current`）；API 34+ 顺序按官方要求走
  —— mediaProjection 型 FGS 起并确认 → `getMediaProjection` → 注册 `MediaProjection.Callback`
  → `createVirtualDisplay`；四个检查点各带 `releasePartial`，失败不留半开会话。
- **同意是一次性的**：API 34+ 每会话重新征询，**不做自动续期** —— 旧的「306s 超时前自动续期」口径
  在 34+ 上做不到（没有可续的持久授权），`docs/design/13-roadmap-budget.md` 的风险表与兼容矩阵
  两处措辞据此订正（`design-decisions.md` 第 44 项）。正路是 `foregroundServiceType="mediaProjection"`
  的前台服务，它本身就免除旧上限；到点（用户撤销 / 系统停止）如实报错并引导重新授权，不假装续上了。
- **幂等与迟到回调**：释放幂等（VirtualDisplay / ImageReader / MediaProjection / FGS）；
  `onProjectionStopped` 按投影身份认领，**先清 `current` 再释放**；迟到的旧回调影响不到新会话。
- **帧**：遵守 `rowStride` / `pixelStride` 拷贝像素、及时 `close` `Image`，经**共享的**
  `ImageAnalyzer.ingest` 入表 —— 与 a11y 截图帧同表同号段，跨帧源匹配（`images.findImage`）才成立。
- **同意征询**：`ScreenConsentRequests` 单请求状态机，`outstanding`（已交给系统）与 `waiter` 分开；
  `revoke` 只撤 waiter、`deliver` 只投当前轮；inbox 忽略非 granted、`claim()` 恰好一次。
  `MainActivity` 用 `registerForActivityResult` 收结果，`requestScreenConsentDetached` 带主线程快路径
  （避免"等自己"），`awaitConsent` 在调用方协程里登记 waiter 并在取消时 `revoke(ticket)`。
- **资源收口**（结构性，不靠记性）：`ConnectionResourceRegistry` 提供 `register(close)` / `revokeAll()` /
  `release()`，恰好一次；撤销后再登记立即触发；teardown 路径上的异常吞进 `onError` 绝不外抛。
  `NewlineFrameServer` 把注册表挂在连接对象上，abort / dispose / EOF 三条路都 `revokeAll()`；
  `AuthenticatedRunContext.resources` 由**接入端**在认证成功后装填（可变字段而非构造参数 ——
  构造点不该认识桥的资源形状）。于是「脚本崩了但投屏还挂着」这条漏在结构上不成立。
- **前台服务与熄屏裁剪**：`ProjectionForegroundService`（`foregroundServiceType="mediaProjection"`、
  `exported=false`）；`ProjectionForeground` **先登记 waiter 再** `startForegroundService`，
  超时 `abandon(generation)`，有界废弃世代集，无 `CountDownLatch`。熄屏收会话（§8.8）：
  keyguard 下投屏给的是**黑帧**，留着只会让脚本拿到黑图还以为成功 —— `ScreenOffGuard` 同步、幂等、不抛。
- **诚实边界**：真机行为未在本机验证（无设备）；`abortConnection` 对「子进程继承了桥 socket fd」
  这一形态**没有覆盖**（那种情况下脚本死了也不产生 EOF），需要 `runId → connectionId` 映射，
  属新范围，未在本批夹带半成品。

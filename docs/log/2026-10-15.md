### 2026-10-15 —— 「该执行不支持暂停」真因：pid 反射阶梯方向反了（用户报，已修）

**用户报**：点悬浮窗暂停 → toast「该执行不支持暂停」。此前（决策 83、本切片「三态真机冒烟补记」
那条）记的口径是「云手机无 root、引擎子进程独立 uid，`kill -STOP` 冻不住」——**那条是误判**，
这次推翻了。**该条目的那段结论不删，在此原地作废**：
~~「暂停在**有 root / 同 uid 可冻**的设备上才生效（本台云手机冻不住 —— 如实 toast，非故障）」~~
—— 本台**就是**同 uid 可冻（`run-as` 发 STOP → rc=0、状态变 `T`），当时的探针只看了
「点按钮没冻住」这个**现象**就归因到设备，没有下探到 pid 那一层。

**推翻的证据（两条，都是设备实测）**：
- 以 **app 自己的 uid** 发信号是成功的：`run-as com.autoscript /system/bin/kill -STOP <pid>`
  → `rc=0`，`ps -A` 里该进程状态变 **`T`**；`kill -CONT` 同样 rc=0。
- 更贴近生产形态的一条：探针脚本（`killtest.js`）让**引擎进程自己**
  `execFileSync('kill', ['-STOP', process.pid])` → 日志里 `KILL-STOP-OK rc=0`，
  且该进程此后一直是 `T`、日志停在同一行（`IF-YOU-SEE-THIS-STOP-DID-NOT-TAKE` 从未打出）。
  **同 uid 能冻，这件事在这台机器上成立。**

**真因**：`ProcessLauncher.pidOf` 恒回 null —— `pauseExecution()` 第一句就是
`val target = pid ?: return false`，于是引擎如实回 false、UI 如实打「不支持暂停」。
pid 为什么拿不到，是**一条反射方向写错**：
- `pid()` 不在 Android 平台 API 表里（android-36 的 `api-versions.xml` 实查：
  `java/lang/Process` 仍只有 destroy/destroyForcibly/exitValue/get*Stream/isAlive/waitFor，
  `java/lang/ProcessHandle` 整类缺席），所以必须走第二级阶梯；
- 而第二级阶梯**从 `Process::class.java` 起步、每轮 `cls.superclass` 往上走** ——
  `getDeclaredField` **只看该类自己声明的成员**，于是这条循环走的是 `Process → Object`，
  **永远够不着子类**；
- 而 pid 恰恰住在**子类**上：设备 libcore（Android 13 `core-oj.jar` 用 dexdump 反编译）
  是 `java.lang.UNIXProcess` 有 `private final int pid`，`java.lang.Process` **一个字段都没有**；
  桌面 JDK 同形（`java.lang.ProcessImpl.pid`，javap 实证）。**所以这条阶梯从来没生效过。**
- 本机用等价 Java 程序把两种走法并排跑过：旧写法回 `null`、新写法（从 `process.javaClass`
  起步）回 `4242` —— 新加的方向门在**修复前会红**。

**影响面不止暂停**（三条同时静默降级）：看门狗因 pid 缺席走 `noPid` 清单、**从不判死**
（`EngineWatchdog`）；`RunIdentityRegistry` 的防劫持检查整段被跳过
（`peerPid != null && spawn.pid != null` 两条件不成立）。

**药**：`var cls = process.javaClass` 起步（与 `:platform:process` 的 `ProcOps.pidOf` 同形
—— 那份方向一直是对的；**两份副本，一处抄漏一行，另一处不会红**，这正是"手法同款代码两份"
的真实代价）。类级 val 改成按调用查的函数（字段住运行时类上，而运行时类每次 spawn 才知道）。

**守卫两条**（形状**照设备抄**，不照实现抄 —— 照实现抄的测试会跟着实现一起错）：
新增 `ProcessLauncherPidTest`（pid 声明在子类上、与运行时类隔两层继承 → 必须取到；
两级都探不到 → 诚实 null，不回 0/自身）+ `ProcOpsTest` 补同形状方向门（钉住那份别被"统一"改回去）。
**全仓此前没有一条测 pid 取值的用例**（只有 `receipt.pid > 0`，桌面 JDK 走 tier 1 就过，
tier 2 从没被执行）—— 这是 bug 能活到今天的原因。

**注释订正三处**：`ProcessImpl` → 设备上其实是 `UNIXProcess`；`pid()` 的可得性从
「Android 14+ 才有」订正为「不在平台 API 表里」；main.cpp 补上「暂停另有前置：pid 必须拿得到」。

**真机回执（2026-10-15 晚，用户实测）**：「暂停能用了」—— 修好后的真形态 APK 上，
悬浮窗暂停按钮实际生效（此前点下去毫无变化 + toast「该执行不支持暂停」）。

### 2026-10-15 —— `console.dir`/`dirxml` 一并接桥（用户令「好」）+ `process.stdout.write` 裁定不做

**用户令**：追问「dir/dirxml/process.stdout.write 这三条收编不了？」之后 ——
「好」（= 把能收编的收编）。

**先纠正我自己的一个误判**：我在上一条目里把 `dir`/`dirxml` 与 `process.stdout.write`
并列成「同一种情况」，说它们「绕开 console 对象直写 stdout」——**前半句对、后半句错**：
两条**原生的确是直写 stdout**（`kWriteToConsole(kUseStdout, …)`，不经五档），但**入口是
console 对象上的自有可写属性**（实测 `own=true writable=true`），所以换得掉。真正碰不到的
只有 `process.stdout.write`。

**落点**（`console-bridge.ts`）：接线表加 `render` 维 + `EXTRA` 两条 → `WRAPPED` 七条。
- `dir` 的渲染 = `util.inspect(obj, {customInspect:false, ...options})` —— 与原生
  `Console.prototype.dir` 的源**同一行**（`node --expose-internals` 读出来的原文；原生多一个
  `inspectOptions(stream)`，在引擎里同值 `{colors:false}`）；异常降级不抛（原生是**冒出去**的）。
- `dirxml` 在 Node 里**就是** `log`（`Console.prototype.dirxml === Console.prototype.log`），
  渲染与送桥照 `log` 抄。
- 两条都送 `log` 档、都不留 stderr 旁路（原生去处都是 stdout，本就被排空）。

**保真证据**：32 种值 × 20 种选项 = **640 组对拍零差异**（含 `depth`/`colors`/`showHidden`/
`maxArrayLength`/`breakLength`/`compact`/`sorted`/`getters`/`showProxy`，值含 Map/Set/类实例/
Error/TypedArray/Buffer/循环/Proxy/Promise/稀疏数组/getter/包装对象/长串/宽对象）；
`dirxml === log` 另 9 组零差异。**唯一的差异一处**：原生按流能力自动上色（TTY / `FORCE_COLOR`），
本包装不上色 —— 引擎里不可见（stdout 是管道、脚本 env 不带 `FORCE_COLOR`，全仓无该变量注入），
但**如实记进 KDoc**：真给脚本注入 `FORCE_COLOR` 就会看到「没有 ANSI 色」。

**唯一裁定不做的**：`process.stdout.write` —— 入口在**流对象**上，收编要接管整个流的契约
（`write()` 的布尔返回值是 Node 文档里的**背压协议**、收 Buffer 的二进制通道、可挂 `cb`），
等于伪造一个 Node 流 API；且「脚本显式写 stdout」正是这次要消灭的那类"替用户改通道"。
**不登记 backlog**（不是欠账，是裁定不做）。

**本机先证伪**（CI 是红绿权威）：真 dist + 抽自 main.cpp 的 kBootstrap + 假 addon 起真 node
—— 正例五条 `BRIDGE console.log`（含 `dir` 的 `{ a: 1, b: { c: [ 1, 2, 3 ] } }`、`dirxml`、
`dir(obj,{depth:0})`、`table`）+ `STDOUT-MARKER` 仍在 stdout；反证（摘掉包装那一句）五条全部
打回 stdout。

**守卫**：`console-bridge.test.cjs` 4→8 例（新增 dir/dirxml 走桥、dir 渲染四族对拍、dir 的
options 是第二参不是第二个值（与 log 的分野）、dir 永不抛）。

**契约同步**（冻结面，作者为维护者本人）：§12.1 边界③、§7.3、决策 84 改写（含"收编不了"那
次误判的订正与 `stdout.write` 的裁定）、main.cpp 注释、示例脚本注释。

### 2026-10-15 —— 裸 `console.log` 走桥（方案 B）：脚本侧语法零改动，通道在引导期换（用户令）

**用户令**：「js 的语法都要和原来的调用方式一样。不然写脚本还得兼容语法」—— 起因是用户拿
一段倒数脚本（IIFE + `setTimeout` + 裸 `console.log`）问「为什么这段代码不会打印出来日志」。
用户先纠正了我「进程启动就退出」的错判（定时器让事件循环保持活跃，代码能正常跑完），
设备 A/B 实测坐实真因：**同一段结构，只把五处 `console.log` 换成 `auto.console.log`，
前者窗口显示「本次执行没有输出（已结束）」、日志文件 0 字节，后者五行齐全带秒差。**

**病**：裸 `console.log` 走 Node 原生 stdout，而引擎排水线程对它**读即弃**
（`ProcessBuilderLauncher`，存在目的唯一 —— 防管道写满反压，§8.3）。行打进了没人看的管道。
「每个脚本都得写 `auto.` 前缀才看得见输出」= 让用户迁就通道实现。

**药（方案 B，用户在两案中选定）**：新增 `bridge/js/src/console-bridge.ts`
（`installConsoleBridge()`），kBootstrap 在 `attachNative` 之后、`require(真脚本)` 之前调它，
把全局 console 五档接到桥上。**范围（用户拍板「1. 覆盖 2. a」）**：五档全包
（log/info/warn/error/debug）；只包**脚本显式调用的 `console.*`**（Node 自身写 stdout 的
路径不经全局 console 对象，照旧排空 —— 窗口里不会混进引擎/Node 内部输出）。

**四条保真边界**：① 格式化用 `node:util.format`（与原生 Console 同一份），返回 `undefined`
不是 Promise（保住「`.then` 当场 TypeError」的原生语义）；② `warn`/`error` **双写**桥 +
原生 stderr（stderr 是诊断面，§8.3 的 `crashSummary`、kBootstrap 自身诊断都读它）；
③ 只包五档 —— `table`/`dir`/`trace`/`assert`/`group`/`time` 与 `process.stdout.write`
仍走原生（仍被排空）；④ **三道守卫缺一不装**（dist env 在位 / `runtimeBridge.installed`
为真 / 包装体 `Symbol.for` 幂等）—— 代价不对称：装了而桥没活着，日志会从「进 stdout
（今天被排空，但至少是真 stdout）」变成「进一条投不出去的面」而且**静默**，守卫不满足就
退回旧形态。失败只打一行 stderr，**脚本照跑**（与 addon/dist 缺位的「选填件不杀执行」同纪律）。
**不挂 `attachNative`**：它在 JVM/桌面测试进程里也被调（`native-bootstrap.test.cjs`），
在那儿包装会劫走测试进程自己的 stdout 标记（`CHILD_DONE` 那类）；`connectBootstrap`
同理不装 —— 那条路 stdout 有人看（终端），没有要解决的问题。

**为什么不是方案 A（引擎把 stdout 接进 ConsoleCollector）**：那条要在排水线程里做行边界
解析 + 归属绑定 + 落盘口径，且把「Node 自身噪声」一并接进来；方案 B 的改动面是 facade
一个新文件 + 引导串一句，语义边界（哪些走桥、哪些留原生）由包装自己一句话说清。

**守卫**：`console-bridge.test.cjs` 4 例（五档都经桥出且 log/info/debug 不写原生 /
`util.format` 保真 + 返回 `undefined` + 循环引用与 BigInt inspect / 幂等不翻倍 /
裸 `console.log` 与 `await auto.console.log` 同一条面）；`BridgeDistPackagingEntryTest`
改断言（裸 console.log 的文本**不该**再出现在 stdout + 显式 `process.stdout.write`
仍在 stdout，一进一出互为对照，新增第 4 关退出码 6）；`DemoScriptTest` 的五行断言

kBootstrap（Python 复刻 `E2EFixtures.extractBootstrap` 的正则）+ 假 addon 起真 node ——

**用户令**（对第 3 条目的追问「暂停功能是有效的吗」之后）：脚本**执行完**，悬浮窗第一颗钮
从暂停图标变成**重新运行**图标；**执行一半停了**（被暂停/被停），变成**继续执行**图标；
长按这颗钮也是重跑。重跑 = **引擎再跑同一文件**（真实重新执行，不是重放旧日志 —— 用户
**拍板**确认）。

**病**：① 执行完点暂停弹「该执行不支持暂停」—— 它已**结束**，不是"不支持"（结算本来就是
暂停的终态）；② 重跑链把窗里的**项目内**形状 relPath（`data/test.js`）直接透传给
`runScriptFileOp`（收**文件清单**形状，首段 = 项目名）—— `AssembledShell.runScriptFile`
的 `ScriptPaths.projectInternalOrNull` 当场 `require` 失败（**2026-10-13 批 73 的教训在
重跑链上复发**，实机表现：点重跑无新 run、toast 被吞）；③ 快速脚本在两轮轮询间起跑即结算、
从没绑上过 → 窗停在「本次执行未开始」。

**药**：
- 内容层（`LogWindowContent`）只看 `state` 画三态图标与文案（`paused → 继续执行` /
  `running → 暂停执行` / 已结算 → `重新执行`），动作由 `MainActivity.windowFirstAction`
  一个地方分派（点与长按同一语义）；`WindowIconButton` 加 `onLongClick`，走全仓
  `pressableLongPress`（`combinedClickable`）；图标复用 `GlyphKind.RUN`，不新增字形。
- **已结算暂停静默早退**：`LogWindowController` 记 `settledRunIds`（`bind` 观察到「仍绑着
  但不再 running」即入账），`togglePause` 对其**一问不问直接返回** —— 不再把「已结束」
  翻译成「该执行不支持暂停」。在途且冻不住 → 如实 toast。
- **重跑**：`windowFirstAction` 对已结算态先 `LogWindowController.rerun`（窗切到新归属的
  重跑态，跑起来后轮询 `bind` 看到同归属新 run 在途自动换绑）再走 `runScriptFileOp`
  （与 ▶ 同一条执行链）；路径**反推首段** = `projectInternalOrNull` 的逆运算（`$projectId/$relPath`，
  窗的 relPath 恒为削过前缀的形状，不会双份前缀）。失败 → toast 原文、窗留重跑态可再点。
- **快速脚本兜底补绑**：`LogWindowState.bind` 增 `fallbackRunId`（从
  `consoleState.scriptOutputLines()` 摘最大非零 runId，`MainActivity` 轮询注入）——
  起跑即结算的脚本在途表一次都没见过也能补绑上，窗画刚跑完的输出而不是「未开始」。
  兜底补位号 running 恒 false、**不进 `settledRunIds`**（不是"被摘走"，是"还没在途过"）。

**守卫**：`LogWindowStateTest` 5 条（兜底补绑 / 已绑过时行摘不顶掉 keep / 引擎外行号不进补位 /
兜底补位号不假充在途且换绑 / 未绑无补位落空态）+ `LogWindowControllerTest` 3 条（结算后
静默早退零 toast / 结算前仍问宿主 / 换绑不记结算）。**口径**：见
[`design-decisions.md`](../design-decisions.md) 第 83 项。**边界**：CI 双工作流绿
（run 38687279767/38687279961；重跑路径修复后 38689478444/38689478505 亦绿）。
**设备冒烟**：装 432bb36 真形态 APK，demo 跑完窗口第一颗钮 `content-desc="重新执行"`
（图标正确从暂停切成重跑）；暂停/继续态与重跑命中的完整链路待用户真机回执
（demo 太快捕不到在途态，需一条长脚本）。

### 2026-10-15 —— 「脚本执行完不要自动清理输出」：悬浮窗结算不解绑（用户令）

**用户令**：脚本执行完**不要**自动清掉输出（日志管理页的脚本输出列表与详情不受影响 ——
那两处是持久落盘，本来就一直在）。

**病**：`LogWindowState.bind` 在 run 离开在途表时把 `boundRunId` 置 null —— 执行一结算，
悬浮窗立刻切回「本次执行未开始」空态，刚跑完的日志在用户眼前被**自动清掉**。在途表是
"正在跑的"这一句，它不含已结算 run 是**事实**，不是**信号** —— 结算去解绑是把
**执行完成**当成了**不存在**。

**药（纯状态层 + 内容层，JVM 可测；无协议面改动）**：
- `bind` 改为**结算不解绑**：同归属在途 run 缺失时保留既有绑定；只有「从开窗起一次都没
  绑上过」（启动失败/门禁拒/起跑即被停）才落空态 —— 失败 toast 已说原因、窗留空态手动关
  （原有语义一字不动）。输出行照旧按绑定 run 过滤（`visible`），窗口保持画刚跑完的那批。
- 状态新增 `running`（绑定 run 此刻在不在途），据此三处诚实：
  `titleText` 结算后缀「· 已结束」；暂停钮 `enabled = running`（跑完了不可暂停，
  点不动也不弹错）；空行区在「已结算且没输出」时改画「本次执行没有输出（已结束）」
  并指路 日志管理 → 脚本输出（内存环 2000 行理论可挤掉本次行，落盘 `ScriptLogStore`
  只追加不会 —— 不把"读不到"说成"没发生"）。
- `ui/detekt-baseline.xml` 随 `WindowIconButton` 加 `enabled` 参数重生成。

**守卫**：`LogWindowStateTest` 三条 —— 结算后保持绑定 + 输出照常可见 + 标题如实缀「已结束」+
已在途的 keep 再出现仍绑回、结算后同归属新 run 换绑到新那条、从没绑上过（启动失败）
仍空态不缀。

**口径**：见 [`design-decisions.md`](../design-decisions.md) 第 82 项。**边界**：CI 双工作流绿
（run 38645518248/38645518135）。**设备冒烟（06:30 装 `11fd5d7` 真形态 APK）**：坐标序列
（项目页 `540 490` → `main.js` 行尾 ▶ `855 662`）跑完 demo —— `script-logs/index.jsonl` 新增
`{"run":7,…}`、`7.log` 五条 demo 行齐全，pid 全程不变（3888）、logcat 无 FATAL/`cannot be saved`；
结算后窗口保持绑定那条路（绑定 run 离开在途表后轮询继续 `bind(empty)` → keep 保留 run 7）在
进程内跑过不崩。窗口内容（标题「· 已结束」/ 行区照常画）属呈现面，由 JVM 测试钉住、真机侧不读屏。

### 2026-10-15 —— 「日志管理→脚本输出→点一行就闪退」：`LoadState` 进不了 saveable 注册表

**用户报**：日志管理 → 脚本输出，选个日志一点就**闪退**。

**根因（设备实测拿到完整栈）**：`ScriptLogDetail` 把详情三态 `load`（`LoadState`）与行
`lines` 放进 `rememberSaveable` —— 而 `rememberSaveable` 会走
`DisposableSaveableStateRegistry.canBeSavedToBundle` 的可接受类白名单
（`Serializable`/`Parcelable`/`String`/`SparseArray`/`Binder`/`Size`/`SizeF`）。
`LoadState` 的三态是 `data object`/`data class`（`NotLoaded`/`Loaded` 是单例对象、
`Failed` 是数据类），**一个都不在白名单里** → 首帧 `requireCanBeSaved` 直接抛：

```
java.lang.IllegalArgumentException: MutableState containing NotLoaded cannot be saved
using the current SaveableStateRegistry
  at androidx.compose.runtime.saveable.RememberSaveableKt.requireCanBeSaved(RememberSaveable.kt:242)
```

异常冒到进程 → 点一行必闪退（用户报的那一下）。**第一版只改了 `lines`**
（`List<String>` 本体是 `Serializable`、空 List 也过，但 `String` 的 `CharSequence`
匿名实现与 `List.subList` 都不是 —— 行形状稍一变就落进同一条），设备复现证明**真正的
首个抛点在 `load`**。

**药**：两个都改 `remember`（详情是**屏内局部现值**，返回即弃，不跨配置存活 ——
配置重建重新拉一次，成本只是一次本地文件读）。`selectedRunId`（`Long?`）留在
`rememberSaveable`：`Long` 是 `Serializable`，那条不在白名单之外。

**设备验证**：修前 APK 用坐标序列（管理 tab → 日志管理 → 脚本输出 pill → 第一行）
必现 FATAL EXCEPTION；修后同一序列 pid 不变、logcat 无 FATAL/`cannot be saved`。

**教训**：`rememberSaveable` 的失败是**首帧即抛**（注册那一刻就校验现值），
不是"配置切换时才炸" —— 因此这类崩溃在真机上是"点开就死"，在 JVM 测试里看不见
（没有真注册表）。凡放进 `rememberSaveable` 的东西都要能回答"它是白名单里的哪一类"。
